# 4단계 대기열 HTTP 사전 부하 시험

## 최신 전체 앱 시험 사용법

아래 후반의 '연결 전' 내용은 최초 준비 기록임. 현재는 실제 로그인·일반 채팅·Agent·임시 SQLite·합성 Chroma 검색을 연결했으며 Gemini만 가짜로 대체함.

```powershell
powershell -NoProfile -File tests/load/run-app-smoke.ps1 -WithChat -DbTrace
powershell -NoProfile -File tests/load/run-app-smoke.ps1 -Realistic -DelaySeconds 10
powershell -NoProfile -File tests/load/run-app-smoke.ps1 -Realistic -DelaySeconds 20
powershell -NoProfile -File tests/load/run-app-smoke.ps1 -Stress -DelaySeconds 10
```

- 한 번에 하나만 실행함. 기존 이미지가 필요하며 새 이미지나 실제 Gemini를 호출하지 않음.
- `Realistic`: 첫 50명 동시 질문 후 실제 60~180초 읽고 각자 한 번 재질문함. 총 100회 시도임. `Stress`: 50개 계정으로 총 1,000회 시도, 응답 후 250ms 간격이며 일부 연결 취소를 섞음.
- 모든 채팅 시험 앞에 정상 일반/Agent, 계정 중복, HTTP/Agent 취소와 빈 기록 정리 검사를 수행함. 이미 저장한 Agent 답변은 보존돼야 함.
- 대기는 15초임. 성공/정원 초과/대기 만료/취소를 구분하며 예상 밖 오류·출처 누락·DB 오류·종료 처리/대기 수 비정상은 실패임.
- `DbTrace`는 DB 작업 종류와 소요 시간만 기록하며 SQL 인자·질문·개인정보를 출력하지 않음.
- 외부 통신이 없는 별도 Chroma를 생성하며 기존 서비스·DB·3001은 연결하지 않음. 앱 CPU 2개·메모리 3891MiB 제한이며 별도 Chroma까지 포함한 VM 전체 제한은 아님. 작은 합성 문서 한 청크이므로 실제 검색 비용·답변 품질·최대 운영 정원을 증명하지 않음.
- 최신 결과와 알려진 한계는 `docs/01_작업일지/2026-10-11_4단계_대기열_사전부하시험.md`를 확인함.

## 검증 범위

실제 `chatAdmission.js`, `chatAdmissionSession.js`를 작은 테스트 전용 HTTP 서버에 연결함. 50개 합성 사용자 번호로 요청하며 로그인 DB 계정을 만들지 않음. 답변·임베딩은 고정 가짜 값이고 실제 API 호출은 없음.

이것은 **SCHAT 전체 부하 시험이 아님**. 실제 로그인, 직원 채팅 API, Agent 도구, Chroma 검색, PDF·문서 자료, Prisma DB 기록, 브라우저 화면은 통과하지 않음. 따라서 이 시험의 낮은 메모리·CPU 수치로 운영 동시 인원을 늘리면 안 됨. 다음 작업에서 전체 앱의 격리 시험을 추가해야 함.

## 실행 조건

노트북 PowerShell의 저장소 루트에서 `powershell -File tests/load/run-local.ps1`로 세 조건을 순서대로 실행함. 하나만 확인하려면 `-Delays 5`를 추가함. 스크립트는 로컬 Docker Desktop 연결만 허용하고, 다른 서버 주소로 실행하지 않음. 기존 같은 이름 테스트 컨테이너가 있으면 충돌 오류로 멈추며 강제 삭제하지 않음.

- 기존 로컬 Docker와 분리된 임시 컨테이너만 사용함. `desktop-linux`의 named pipe 연결임을 먼저 확인함.
- `--network none`: 외부 통신 금지. 실행 스크립트도 기본 네트워크 경로가 있으면 거절함.
- API 키·DB·storage·원본을 전달하지 않음. 테스트 폴더와 대기열 코드 3개만 읽기 전용으로 연결함.
- 이미 있는 `node:18-slim` 이미지 사용, 새 이미지 빌드·내려받기 없음.
- CPU 2개, 메모리 3891MiB(약 3.8GiB). 이 사전 시험은 swap을 추가 허용하지 않음. VM의 기존 swap 사용 1.3GB를 재현한 것이 아님.
- `--rm`은 이 실행으로 만든 임시 컨테이너만 종료 후 정리함. 영구 볼륨을 만들거나 삭제하지 않음. 기존 3001 컨테이너는 건드리지 않음.

## 요청 방식과 해석

- 지연 5초·10초·20초별 5,000 **시도**임. 5,000개 모두 성공해야 한다는 뜻이 아님.
- 50개 작업자가 각자의 합성 사용자로 연속 질문함. 응답·거절 후 250ms 쉬고 다시 시도함.
- 17번째마다 2초 뒤 연결을 끊음. 대기 중 또는 답변 중 닫기를 모사함.
- 동시 생성 4건·대기 최대 10건의 실제 코드를 사용함. `e72af281` 이후 대기는 15초·생성은 80초임(이전 시험은 대기 30초). 성공, 정원 초과, 대기 만료, 취소를 구분해 출력함.
- 전체 요청 지연과 성공 요청의 지연은 따로 표시함. 즉시 거절된 요청 때문에 전체 평균이 빨라 보이는 착시를 피함.
- CPU는 같은 컨테이너의 테스트 서버+요청 발생기 프로세스 평균 사용률이며 2개 코어 전체 대비 비율임. 메모리·swap은 100ms 간격 cgroup 표본 최댓값임.
- 끝난 뒤 active=0·waiting=0, 최대 active≤4·waiting≤10, 예상하지 않은 오류 없음이어야 함.

현재 파일은 사전 시험 코드이며 운영 설정에 가짜 모드를 추가하지 않음. 4단계 전체 완료 판정·동시 수 상향 추천은 전체 앱 검증 이후에만 가능함.

## 전체 앱 격리 준비 — 2026-10-11 추가

`powershell -NoProfile -File tests/load/run-app-smoke.ps1`은 실제 앱의 **시작·로그인만** 검사함. 직원 질문 부하 시험은 아직 아님.

- 기존 `schat-local-schat-web:latest` 이미지의 의존성과 현재 서버 소스를 사용함. 앱 소스는 명시한 폴더만 읽기 전용으로 연결함.
- 네트워크 없음, 포트 공개 없음, 빈 tmpfs storage 사용. 이미지의 `.env`도 `empty-config.txt`로 가림. 기존 DB·키·문서를 연결하지 않음.
- 새 임시 DB에 현재 마이그레이션을 적용하고 직원 50명·관리자 1명을 생성함. 비밀번호·서명키는 실행마다 메모리에서 임의 생성하며 출력하지 않음.
- 실제 `/api/request-token` 로그인과 관리자 대기열 조회를 검사함. 검색 저장소와 가짜 Gemini는 아직 연결하지 않았으므로 채팅 질문은 보내지 않음.
- 네트워크 차단으로 모델 목록·가격표 갱신 오류가 기록될 수 있음. 의도된 외부 조회 차단이며 로그인 통과와 따로 해석함.
- 종료 시 이 시험 컨테이너와 임시 DB만 사라짐. 기존 컨테이너는 변경하지 않음.

## 현실적인 사용 패턴 도구 — 아직 전체 앱 연결 전

`realisticWorkload.cjs`는 50개 계정에 연결할 요청 함수를 받아 각 계정이 질문 완료 후 실제 60~180초를 쉬도록 구성함. 기본 3회씩이며 첫 질문은 동시에 시작함. 거절된 계정도 같은 간격을 두고 재시도함. 대기 시간을 줄여 실행하는 단위 검사는 실제 부하 결과로 사용하지 않음.

집계 기준:

- 정원 초과 비율: `SCHAT_QUEUE_FULL / 전체 시도`. 대기 30초 만료는 별도로 집계함.
- 평균 대기: 실제 생성 입장까지 측정된 시간만 사용함. 즉시 입장(0초)을 포함한 평균과 실제 줄 선 요청 평균을 나눔. 답변 생성 시간과 합치지 않음.
- 대기 측정값이 없으면 0으로 간주하지 않고 미측정 건수로 남김.
- 처음 50명 동시 질문(`initial`)과 이후 반복(`repeat`)을 분리해서 보고해야 함.
- 전체 앱 요청 연결, 실제 순번 이벤트에서 입장 시간 측정, 5/10/20초 반복 실측은 다음 작업임. 현재 거절률·평균 대기 실측 결과는 없음.
