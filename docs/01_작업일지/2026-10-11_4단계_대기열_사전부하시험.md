#### Agent/취소 연결 검사에서 발견한 추가 문제

- 실제 Agent WebSocket에서 가짜 답변 수신과 정상 종료를 확인함. 같은 직원의 중복 질문은 `SCHAT_DUPLICATE`, HTTP 및 Agent 중단은 `CLIENT_CANCELLED`, 이후 관리자 조회는 처리 0·대기 0이었음.
- 그러나 이 실행의 서버 로그에는 `prisma.workspace_chats.deleteMany()`의 `ConnectionError(Timed out during query execution.)`가 두 차례 나타남. 최초 도구는 종료 코드 0을 냈으나 **이 실행을 전체 통과로 인정하지 않음**. 후속 도구는 `prisma:error` 로그가 있으면 실패로 종료하도록 보완함.
- 읽기 전용 코드 조사에서 Agent의 미응답 대화 정리 경로 `server/utils/agents/aibitat/plugins/chat-history.js` → `WorkspaceChats.delete`가 해당 쿼리를 사용함을 확인함. 취소·저장 동시성 또는 격리 DB 환경 때문인지는 아직 확정하지 않음. 이번에 운영 코드나 DB 정책을 바꾸지 않았으며 실제 자료를 삭제하지 않음.
- 이 문제의 독립 재현과 원인 분리가 다음 우선 작업임. 대기열 숫자 정상 복귀만으로 대화 저장까지 정상이라고 판단하지 않음.
- 같은 빈 DB 시험을 다시 실행하자 동일한 DB 쿼리 시간초과 로그 1회가 재발함. 보완한 도구가 종료 코드 1로 실패 처리함을 확인함. 정상 Agent 답변, 중복 차단, 양쪽 취소, 처리/대기 0은 재확인했으나 DB 오류 때문에 전체 통과가 아님. 실패가 일반 직원의 실제 운영 데이터에서도 발생한다는 의미는 아니며 별도 재현 분리가 필요함.

## 시험 방식

- 50개 합성 사용자 번호가 각자의 요청을 연속 전송함. **실제 로그인 계정 50개 시험이 아님.**
- 지연 5초·10초·20초마다 5,000회 시도함. 가짜 임베딩+가짜 답변의 합산 지연임. 성공 5,000건을 뜻하지 않음.
- 응답 또는 거절 후 250ms 쉬며 17번째 시도마다 2초 뒤 연결을 끊음. 정원이 찼을 때 거절된 요청은 취소 시각 전에 끝날 수 있음.
- 실제 공통 대기열·HTTP 연결 종료 처리를 재사용함. 본 앱의 직원 채팅 API·Agent WebSocket 자체를 부하 호출한 것은 아님.
- CPU는 요청 발생기까지 포함한 프로세스 평균이며 2개 코어 대비 비율임. 메모리·swap은 100ms 간격 cgroup 표본의 최댓값임. 순간 최댓값을 보장하지 않음.

## 해석

이 폭주 조건에서는 대기열 정원에 먼저 걸림. CPU·메모리가 낮다는 이유로 운영 동시 수를 올리면 안 됨. 검색·DB·실제 Agent가 빠진 가벼운 시험 서버이기 때문임. **전체 앱 시험 전에는 기본 4건 유지**를 제안함. 안전하게 올릴 수 있는 최대치는 아직 판단하지 못함.
