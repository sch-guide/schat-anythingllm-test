# 답변 근거 보기 — 문서명별 목록

## 요청과 원인

- 같은 PDF가 등록 번호별로 반복되는 선택창을 실제 문서명 한 줄로 묶도록 요청받음. commit/push/tag 금지.
- 기존 미커밋 개선은 PDF 번호·버전 기준이라 같은 이름이어도 내부 번호가 다르면 여러 줄로 남았음.

## 구현

- 조회 계층에서 실제 이름(NFC 정규화·경로 제외·앞뒤 공백 제외)으로만 표시 묶음을 만듦. 이름 없는 자료는 등록 번호로 분리해 잘못 합치지 않음. 부서 범위는 기존대로 유지.
- 선택 항목의 대표 등록 번호로 같은 이름의 모든 등록 기록을 찾아 각 문단 연결을 읽음. 문단을 저장소에서 합치거나 지우지 않음. 쪽 순서·다음 목록·단어 검색 유지.
- 각 문단에 해당 등록 기록의 문서 번호·버전·쪽·이전 버전 상태를 붙임. 한 묶음의 대표 버전을 다른 문단에 덮어씌우지 않음.
- 새로고침은 동일 API를 사용하므로 같은 기준 적용. 질문별 보기는 문서 선택창이 없는 구조라 기존 출처별 조회를 유지하고 관련 회귀 검사를 실행함.
- RAG/BM25/Vector/Chroma 저장 구조 및 원본 PDF 연결 변경 없음. 다른 창의 미커밋 수정은 보존.

## 검증

- 이름이 같고 등록 번호가 서로 다른 가짜 자료에서 수정 전 중복 목록 발생 → 수정 후 한 항목을 확인.
- 가짜 검사: 요청한 세 문서 각 1개, 모든 등록 문단 조회, 문단별 버전과 쪽수 보존, 이전 자료 상태 보존, 새로고침 결과 동일, 원래 자료 불변.
- 가짜 60쪽을 두 목록에 걸쳐 1~60쪽 모두 조회. 조회·화면·권한 총 29개 통과.
- 실제 로컬 SQLite를 읽기 전용으로 열어 수정된 목록 함수를 실행한 결과: 검사 및 시술(26.04.07).pdf 1개/82쪽, 2026실무지침서 (26.7).pdf 1개/461쪽, 수술(260306).pdf 1개/40쪽. 병원 원문을 출력하지 않음.
- 실제 브라우저의 새 화면이나 운영 서버 결과를 확인한 것은 아님. 3001/운영 서버에 반영하지 않았음.

## 상태

당시 코드와 검사 완료, 미커밋·미배포였음. 후속 2026-10-14 작업에서 로컬 3001에 반영하고 실제 문서 전체 조회를 확인함. 상세 백업·조회 결과는 `2026-10-14_답변근거_3001반영.md` 참조. 실제 Gemini 호출·DB 구조 변경·자료 삭제·commit/push/tag·운영 반영 없음.
