# 3단계 보완부터 7단계 — 진행 기록

## 승인 범위와 시작점

- 저장소 `schat-anythingllm-test`, 기본 대기열 커밋 `4457bfd1`에서 이어감. 오늘 작업일지와 기존 미커밋 변경을 확인하고 보존함.
- 단계별 검증 뒤 해당 단계만 커밋함. push·운영 서버 작업 금지. 실제 Gemini 호출은 7단계 최대 5회 외에는 하지 않음.
- 사용자 제공 한도: 답변 Gemini 3.8 Flash, Tier 1, RPM 1,000·TPM 200만·RPD 10,000. 이 값은 API로 재조회한 값이 아님.
- VM CPU 2개·메모리 3.8GB·스왑 4GB 중 1.3GB 사용. 동시 생성 4건은 부하 시험 전 설정이며 안전 인원 보장이 아님.

## 3단계 구현

- 대기열 30초와 생성 제한을 분리함. 서버는 입장 후 90초, 화면은 입장 이벤트 수신 후 100초로 맞춤. 과거 방식 C 측정의 4~69초를 참고한 임시 추천값임. 이번에 실제 Gemini 응답 시간을 재측정하지 않음.
- 질문을 보낸 시각 대신 입장한 시각을 저장하며, 같은 질문 다시 생성·수정 재전송은 시각을 초기화함. 화면의 100초 제한은 일부 답변이 이미 보이는 스트리밍에도 적용함.
- 일반 Gemini·Agent Gemini의 답변 전송 경계에서 모델별 호출 시도를 셈. SDK가 같은 전송 경계를 재시도하면 추가 집계하며 실패 호출도 포함함. 캐시 등 모델 전송이 없는 경로는 집계하지 않음. 답변 캐시 자체는 아직 구현하지 않음.
- 관리자 시스템 상태에 기본 답변 모델의 `오늘 ○ / 10,000건`과 70% 이상 주의 안내를 표시함. 모델별 저장이므로 다른 모델의 수를 기본 모델에 합치지 않음.
- 날짜는 `America/Los_Angeles` 기준으로 계산함. 한국 시간 오후 4시(미국 서머타임)·오후 5시(표준시)에 날짜가 바뀜.
- 기존 `system_settings`에 `schat_gemini_daily_usage`만 저장함. DB migration 없음. 키·질문·원문은 저장하지 않음. 첫 집계 시작 시각을 표시하며 이전 사용량을 소급 추정하지 않음.
- 집계 쓰기를 답변 전송보다 먼저 기다리지 않도록 함. 저장 장애가 답변을 막지 않으며, 확인 불가 때 숫자 0을 정상값처럼 표시하지 않음. 갑작스러운 프로세스 종료 직전의 미저장 기록은 손실 가능함.

### 집계의 뜻과 한계

Google의 실제 전체 RPD·남은 잔액이 아니라 이 Node 서버의 두 Gemini 답변 공급자 경로에서 관측한 호출 시도임. 다른 서버·RAGAS·직접 Gemini 호출 경로는 포함하지 않음. 임베딩 모델은 별개임. 관리자 화면의 모델은 서버 기본 답변 모델이며 작업 공간이 다른 모델을 사용하면 그 모델 수와 다를 수 있음. 이 숫자만으로 직원 질문을 차단하지 않음. 실제 429 오류 알림·월 토큰 예산 추정과도 별개임.

### 검증

- 가짜 호출·HTTP/Agent 연결·권한·취소·기존 검색 회귀 검사 56개 통과함. 실제 API·운영 DB는 호출하지 않음.
- 대기 29초 후에도 생성 90초 보장, 만료·닫기 후 자리 반환, 재생성 시각 초기화, 여름·겨울 날짜 경계, 재시작을 모사한 저장값 복원, 동시 카운터 쓰기, 최초 조회/집계 경쟁, 70% 경계, 저장 장애 시 답변 진행을 확인함.
- 읽기 전용 코드 검토의 주요 지적(재생성 시각·최초 읽기 경쟁·저장 때문에 답변 지연)을 재현 검사 후 수정함.
- `git diff --check` 통과함. 화면 이벤트 검사에 기존 import.meta/CJS 경고가 남음.
- production build와 문서 화면 검사는 아래 최종 결과에 기록함. 실제 브라우저 100초 중단과 실제 SDK 재시도 통합 검증은 아직 별도 확인 대상임.

## 이후 순서와 다음 시작점

1. 3단계 최종 빌드·문서 검사·선별 커밋 결과를 아래에 기록함.
2. 4단계: 기존 3001·운영 자료와 분리된 노트북 Docker 환경을 준비함. 답변·임베딩 가짜 호출, CPU 2·메모리 3.8GB, 50개 합성 계정, 5/10/20초 지연별 5천 요청과 취소를 검사함. 현재 실행하지 않음.
3. 5단계: 보수적인 동일 질문 캐시와 관리자 조회. 의료 용량의 소수점·음수·단위 의미가 사라지지 않도록 정규화 검사부터 작성함. 전체 100개, 작업 공간 격리, 문서 변경 시 비우기, 대기열·호출 집계 우회함. 현재 미구현임.
4. 6단계: 관리자 청크 조회만 구현함. 이전 버전 표기와 질문 근거 연결, 직원 권한 차단을 검사함. 현재 미구현임.
5. 7단계: 실제 모델의 seed 지원 공식 확인 후 설정·temperature 안내 및 같은 합성 질문 최대 5회 확인함. 현재 미구현·실제 호출 0회임.

문서 업데이트 작업일지는 안전 차단 `DOCUMENT_UPDATE_READY=false`가 남았다고 기록함. 이번 단계에서 이를 해제하지 않음. 5단계 연결은 기존 안전 차단을 유지한 채 성공한 문서 변경의 캐시 무효화 경계를 확인해야 함.

## 로컬 확인과 운영 반영

현재 실행 중인 Docker 3001에는 이번 코드를 반영하지 않음. 반영 후 관리자 → 시스템 상태에서 처리/대기 수와 하루 집계를 확인할 수 있음. 지금 3001에서 실제 질문을 하면 Gemini 호출이 발생할 수 있으므로 가짜 환경 준비 전 부하 질문을 보내지 않음.

운영 서버 배포는 모든 단계가 끝난 후 사용자가 진행할 별도 작업임. 그때 백업·배포·서비스 정상 확인 뒤 `sudo docker builder prune -f`로 빌드 캐시만 정리함. DB·Chroma volume·storage를 지우거나 `down -v`를 사용하지 않음.

## 3단계 최종 검증과 커밋 준비

- 관련 자동 검사 최종 56개 통과, Vite production build 및 postbuild 성공(45.64초), 문서 화면 재생성·분리 검사 11개 통과함.
- 기존 브라우저 호환 목록·음성 라이브러리 서버 모듈 참조·큰 파일 묶음 경고와 문서 생성기의 escape sequence 경고는 남아 있음. 신규 검증 실패 없음.
- 다른 작업의 코드·문서·storage·DB migration은 이번 커밋에서 제외함. 공용 현재 상태 문서는 이번 3단계 한 줄만 선별함. 생성 문서 화면은 여러 미커밋 작업을 함께 반영하므로 로컬 갱신만 하고 통째로 커밋하지 않음.
- 기존 pre-commit 자동 stage가 다른 작업의 생성 문서를 포함하지 않도록 이 커밋에만 hooksPath를 비워 실행함. Git 설정은 바꾸지 않으며 문서 검사는 위에서 직접 실행함.
- 실제 브라우저·Docker 적용·운영 배포는 하지 않음. 다음 시작은 4단계 격리 Docker 가짜 부하 환경 준비임.
