# 2026-09-26 · 이미지 설명 전체 보충과 자동 증분 처리

## 무엇을 바꾸었나

- 새 PDF를 올릴 때 이미지를 SHA-256 hash로 구분하고, 이미 처리한 hash는 Gemini에 다시 보내지 않도록 했습니다.
- 새 hash만 설명을 만들고, 성공·빈 응답·실패 상태를 즉시 cache에 저장하도록 했습니다.
- 25~50개 단위 배치 진행상태를 저장하고, 중단 후 다시 실행해도 완료된 hash를 재호출하지 않는 backfill 도구를 추가했습니다.
- 이미지 설명 생성이 실패해도 PDF 본문 등록은 계속되는 기존 안전 경로를 유지했습니다.

## dry-run과 실제 실행

- 고유 이미지: 1,172개
- 기존 설명: 34개
- 신규 Vision 대상: 1,138개
- 배치: 23개
- 실제 Vision 호출: 1,138회, 재시도 0회
- 성공: 882개
- 빈 설명: 0개
- 실패: 256개

실패는 Google API의 사전 결제 크레딧 소진 이후 발생했습니다. 요청한 정책대로 실패 hash를 기록하고 재시도하지 않았습니다.

## 보조 벡터 반영 상태

- 성공한 설명은 문서 metadata와 hash cache에 저장됐습니다.
- 결제 복구 뒤 새로운 Vision 설명을 만들지 않고 cache에 성공 저장된 설명만 Embedding했습니다.
- 기존 고유 이미지 설명 벡터 34개를 제외한 신규 대상 882개를 4개 단위, 총 221개 Gemini Embedding 요청으로 처리했습니다.
- 882개 모두 Chroma에 추가됐고 Embedding 실패는 0개입니다.
- live 이미지 보조 벡터는 63개에서 945개가 됐습니다. 고유 설명은 916개이고, 나머지 29개는 작업 전부터 존재한 중복 벡터입니다.
- 기존 본문 벡터는 작업 전후 654개로 동일하며 snapshot hash `479527c9ac5ec8b2cec31dde660cd47188a7600ccbdecba1a2771888238fe43b`도 같습니다.
- 각 Embedding batch를 Chroma에 반영한 직후 진행상태를 저장하므로, 중단 후 재실행해도 이미 반영된 안정적 `문서 + image_key` 벡터는 다시 생성하지 않습니다.

## Vision 실패 256개

- 이번 작업에서는 실패 hash를 Vision에 다시 보내지 않았습니다.
- 저장된 실패 record에는 세부 오류 유형이 남아 있지 않습니다. 다만 기존 실행에서 크레딧 소진 직후 연속으로 실패했고 최종 API 응답이 HTTP 402였으므로 운영상 256개 모두 `결제/쿼터`로 집계했습니다.
- 이미지 읽기 오류, 지원하지 않는 이미지, 기타 API 오류로 확인된 별도 건수는 0개입니다. 이 분류는 hash별 원인 로그가 아니라 당시 실행 순서와 확인된 402 응답에 근거합니다.

## 사용자가 알 사항

앞으로 PDF를 올릴 때는 별도 전체 backfill 명령이 필요하지 않습니다. 같은 이미지는 cache를 재사용하고, 새로 추가되거나 내용이 바뀐 이미지만 새 hash로 처리됩니다. 현재 설명을 보유한 916개 고유 이미지는 모두 보조 벡터 검색 후보로 반영됐습니다. 실패 256개는 별도 승인 전까지 Vision 재시도 대상에서 제외됩니다.
