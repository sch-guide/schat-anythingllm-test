# 문서 업데이트 서버 구현·검증 기록 — 2026-10-10

## 현재 판정

기존 자료와 분리해서 새 PDF를 준비하고, 검색 자료를 바꾸거나 복구하는 실제 서버 경로를 작성했다. 다만 모든 기존 업로드 경로와의 동시 작업 방지가 완성되지 않아 **기능 완료·배포 가능으로 판정하지 않는다**. 실제 운영 자료, 기존 DB, Chroma, 병원 원문은 수정하지 않았다. 외부 AI를 호출하지 않았고 commit·push·Docker 재배포도 하지 않았다.

미검증 경로가 실수로 활성화되지 않도록 내부 `DOCUMENT_UPDATE_READY=false` 차단을 연결했다. 인증·권한 확인을 통과해도 파일 수신 전에 503과 “안전 검증이 끝나지 않아 업데이트를 사용할 수 없습니다.”를 반환한다. 환경변수로 우회하는 설정은 없다. 아래 서비스 동작은 직접 호출한 격리 검증 결과이며 현재 사용자 화면에서 실행 가능한 기능이 아니다.

## 작성한 서버 경로

- `POST /workspace/:slug/document-update`: 로그인, 관리자·관리자급 역할, 작업 공간 접근 권한을 확인한 뒤 파일을 받는다.
- 요청은 multipart `files` 배열과 `manifest` JSON이다. manifest는 `{names, conflicts, folderName?}`이며 conflicts는 직전 사전 확인 결과다.
- 현재 실제 구현 대상은 PDF 묶음과 Chroma다. 다른 형식이나 다른 검색 저장소, 다른 작업 공간과 공유된 문서, 자동 동기화 문서는 안전상 거절한다. 기존 일반 업로드로 대신 처리하지 않는다.
- collector는 새 UUID 작업 폴더에 PDF의 페이지 JSON을 쓴다. 기존 PDF 이미지 처리 기능은 유지한다. 기존 `parseOnly`를 사용하지 않아 이미지 처리를 끄지 않는다.
- 새 원본 PDF에는 새 식별자를 부여한다. 새 검색 자료는 별도 Chroma collection에 준비하고 새 문서·벡터 매핑을 검사한다.
- 디스크에 남는 배타 잠금과 읽기·쓰기 사용 표시를 사용한다. Chroma 검색·쓰기, 문서 추가·제거, 고정 문서, 문서 삭제 등에 연결했다. 사용 중이거나 복구 잠금이 남아 있으면 중단한다.
- 잠금 안에서 이름 충돌을 재확인하고, 기존 벡터와 DB 행을 복구 기록으로 저장한 뒤 새 자료 설치, 이전 벡터 제거, DB 보관 표시, 검색 캐시 폐기 및 새 목록 검사를 진행한다.
- 이전 문서 DB 행과 원본은 보존한다. 보관 행에는 `schat_document_update_archived:true`를 기록하고 고정·자동 동기화를 해제한다. 보관 행 조회·삭제 방지는 별도 담당자가 구현했다.
- 이전 체크리스트·퀴즈·과거 답변의 연결을 새 문서로 바꾸지 않는다. 응답은 관련 체크리스트·퀴즈 묶음·과거 답변의 식별자와 제목 목록을 포함하고, 대화 본문은 반환하지 않는다.
- 테스트·평가용 문서를 직원 검색 대상으로 바꾸지 않도록 기존 `usage_scope`를 유지한다. 이름이 같은 이전 자료들의 용도가 서로 다르면 거절한다.
- 중간 실패 시 기존 벡터·DB·파일 목록을 되돌린다. 복구 실패는 잠금과 복구 기록을 보존한다. 교체 검증 후 잠금 해제만 실패한 경우에는 이미 검증된 새 자료를 다시 바꾸지 않는다.
- 런타임 복구 기록은 `.gitignore`의 전용 경로로 Git 유입을 막았다. 복구 기록에는 원문 조각이 포함될 수 있으므로 공유하거나 커밋하면 안 된다.

## 테스트를 먼저 실패시킨 확인

잠금 모듈과 격리 목적지 모듈을 추가하기 전에 해당 기능이 없어서 실패함을 확인했다. 서비스 입력·벡터 검증도 모듈이 없는 상태에서 실패를 확인했다. 이후 DB 매핑 없는 이전 벡터, 테스트 문서 용도 보존, 교체 검증 뒤 잠금 해제 실패 사례는 실제 기대 동작이 나오지 않는 실패를 확인하고 코드를 보강해 통과시켰다.

전체 성공·복구 흐름 검증은 서비스 초안을 작성한 뒤 추가했다. 따라서 전체 구현의 모든 동작을 엄격하게 테스트 우선 방식으로 작성했다고 주장하지 않는다.

## 자동 승인 검토로 막힌 확장과 남은 위험

기존 공통 파일 업로드·API 업로드·Collector 처리까지 잠금에 참여시키려는 추가 패치는 자동 승인 검토에서 거절됐다. 거절 이유는 “문서 업데이트와 무관한 기존 모든 파일 업로드·API 업로드·Collector 처리까지 전역 잠금으로 감싸 서비스 전체 동작을 바꿀 수 있어, 승인된 기능의 범위를 넘어 장애 위험이 큼”이었다. 거절된 공통 래핑은 적용하지 않았고 우회하지 않았다.

현재 일반 작업 공간 파일 업로드 한 경로에는 사용 표시가 연결되어 있으나, 다른 API 업로드·Collector 기반 등록·폴더 이동 등 모든 기존 문서 변경 경로를 포괄하지 않는다. 다른 경로가 새 자료를 쓰는 시점과 교체 확정 시점이 겹치면 목록 재확인만으로 원자성을 보장할 수 없다. **진행 중 작업을 한 번 조회한 뒤 업데이트를 진행하는 대안도 조회 직후 새 업로드가 시작될 수 있어 충분하지 않다.**

따라서 다음 작업에서는 기존 업로드 경로까지 영향을 주는 동시 작업 제어 범위를 명시적으로 결정하거나, 문서별 충돌만 직렬화하는 더 좁은 설계를 검토해야 한다. 이 문제가 풀리기 전에는 현재 경로를 운영에 배포하지 않는다.

추가 확인 항목:

- 성공 이후 격리 collection 정리 실패는 현재 무시하므로 경고 반환 및 관리자 정리 기록을 보강해야 한다.
- 준비 중 부분 실패로 남은 격리 벡터·새 이미지·새 원본의 장기 보관/정리 정책을 검토해야 한다. 기존 원본은 제거하지 않는다.
- Chroma가 받은 벡터 개수·식별자·형식을 검사하나, 임베딩 공급자가 일부 조각만 반환하는 경우까지 새 PDF의 모든 검색 조각이 준비됐는지 추가 검증이 필요하다.
- 관련 목록은 퀴즈 묶음 중심이다. 묶음에 소속되지 않은 퀴즈 문제와 다양한 과거 출처 형식까지 빠짐없이 집계하는지 확인해야 한다.
- 실제 PDF 원본 내려받기, 고정 문서·목록·저장공간 정리, 실제 Chroma의 BM25·검색 캐시를 한 흐름으로 확인해야 한다.
- 비정상 종료 시 남은 읽기·쓰기 표시나 배타 잠금은 자동 삭제하지 않는다. 실제 진행 중 작업 여부와 작업 폴더의 복구 기록을 대조한 뒤 관리자가 복구해야 한다. 자동 복구 명령은 아직 없다.

## 기존 독립 교체 함수

`transaction.js`는 이전 작업의 독립 교체 제어 함수로 남아 있다. 새 서비스는 PDF 묶음 준비, 실제 DB·검색 저장소·복구 기록, 검증 완료 후 잠금 해제 실패 처리를 위해 별도 흐름을 사용하며 이 함수를 호출하지 않는다. 이전 작업 보존 조건 때문에 해당 함수와 기존 테스트를 임의로 삭제하지 않았다. 유지·정리 여부는 전체 검토 뒤 결정한다.
