# 동시 답변 제한 — 구조 조사 및 설계 검토

후속 승인: 사용자가 초기값을 생성 4건·대기 10건으로 변경해 승인함. 아래 2건·4건은 최초 제안의 기록이며 현재 기준이 아님. [승인 후 조사와 진행 상태](2026-10-10_동시답변_제한_구현진행.md)를 이어서 확인함.

## 현재 진행 상태

- 사용자 요청: 동시 답변 수 제한, 관리자 설정, 대기 순번, 30초 대기 제한, 계정당 1건, 오류·종료 시 자리 반환, 완료 후 별도 commit. push 금지.
- 기능 구현·테스트·commit은 아직 하지 않음. 설계 승인 단계임.
- 기존 미커밋 변경이 많음. 문서 업데이트·출처 표시·Gemini 알림 등 다른 작업을 이번 커밋에 섞지 않아야 함.

## 확인한 실제 코드

- `server/endpoints/chat.js`: 일반 작업 공간과 스레드 채팅 API가 각각 있음. 기존 인증과 사용자 일일 질문 수 검사 후 답변 경로를 실행함.
- `server/utils/chats/agents.js`: Automatic/Agent 모드는 HTTP 응답에서 WebSocket으로 전환함. HTTP가 끝났다는 이유만으로 처리 자리를 반환하면 실제 Agent 생성이 제한 밖에서 실행될 위험이 있음.
- 따라서 일반 답변과 Agent 답변의 실제 시작·종료를 함께 추적해야 함. WebSocket 연결 대기·중복 연결·연결 실패 처리도 필요함.

## 승인 요청할 설계

- 현재 단일 서버 프로세스 안에서 공통 대기열을 관리함. 여러 서버/프로세스로 확장할 경우 공유 저장소 방식으로 전환해야 함.
- 임시 기본값: 동시 생성 2건, 대기 4건, 최대 대기 30초. 서버 사양만으로 보장된 성능값은 아님.
- 로그인 사용자 ID 기준으로 처리 중과 대기 중을 합해 계정당 1건만 허용함. IP로 사용자 구분하지 않음.
- 관리자 설정은 기존 설정 저장소 사용. 처리 중·대기 중 수는 실시간 상태임. 서버 재시작 뒤 오래된 숫자를 복원하지 않음.
- 정상 종료·예외·연결 종료·대기 만료에서 중복 반환을 방지하고 자리 회수. 생성 시간 제한은 우선 120초를 제안하되 실제 취소 전달 경로를 확인해야 함. 숫자만 먼저 줄이고 AI 호출을 계속 남기는 방식은 금지함.
- 직원에게 SCHAT 순번 대기와 Gemini 요청 제한을 서로 다른 상태/설명으로 표시함.
- 관리자가 한도를 줄이면 기존 답변은 강제 중단하지 않고 새 입장부터 제한함.

## 테스트할 항목

동시 2건 초과 시 대기, 순번 갱신, 30초 만료, 대기열 가득 참, 여러 탭 중복 요청, 대기 중 창 닫기, 생성 중 창 닫기, 예외, 생성 시간 초과, Agent 전환, 중복 종료, 설정 변경, 관리자 권한, 기존 질문 경로 회귀를 가짜 호출로 확인해야 함.

## 한도 숫자를 받은 뒤 계산 방법

모델별 남은 RPM ÷ 질문당 호출 횟수, 남은 TPM ÷ 질문당 전체 입력 토큰 중 작은 질문/분 값을 구함. 임베딩 및 다른 Gemini 작업의 사용량도 따로 고려함. 평균 처리 중 수는 질문/분 × 응답 시간(초) ÷ 60으로 참고하되 순간 몰림·느린 요청·메모리 부하는 별도 시험함. 계산값은 최대 인원 보장이 아니며 여유를 두고 부하 테스트로 조정함.

## 다음 시작 위치

설계 승인 후 Agent WebSocket/취소 연결을 추가 조사하고 세부 구현 계획을 작성함. 실패 테스트부터 작성하여 서버 공통 제어 → 직원 순번 표시 → 관리자 설정/현황 → 회귀 검증 순으로 진행함. 완성 뒤 이번 변경만 별도 commit하며 push하지 않음.
