# 동시 답변 제한 — 승인 후 조사와 구현 진행

## 승인된 기준

동시 생성 4건, 대기 최대 10건, 최대 대기 30초, 생성 제한 120초, 로그인 사용자당 처리·대기 합계 1건임. 관리자 설정으로 처리 한도를 조정함. CPU 2개·메모리 3.8GB·스왑 4GB 중 1.3GB 사용이라는 사용자 보고를 기준으로 하되, 4건은 부하 시험 전 임시값임. 완료 후 이 기능만 commit, push 금지임.

## 구현 전 요청한 5가지 확인

### 1. 질문 한 건의 모델별 호출 수

실제 API를 호출하거나 운영 기록을 측정하지 않았음. 아래는 로컬 코드의 논리 호출 경로이며 SDK 재시도 횟수까지 포함한 실제 요청 건수는 아님.

- 일반 채팅: `server/utils/chats/stream.js`에서 보통 선택된 답변 모델을 1회 호출함. 스트리밍/비스트리밍은 서로 다른 분기라 합쳐 2회가 아님. 문서 없음·안전 검사 사전 거절 등은 0회일 수 있음. 별도 모델 라우팅/SDK 재시도 설정이 있으면 추가 호출 가능함.
- 검색: `expandedBodySearch.js`는 원질문과 변형 검색어를 합쳐 최대 4개 검색함. `chroma/index.js`는 `searchCache.embedWithCache`를 사용하므로 캐시 적중 시 외부 임베딩은 0회임. 관련 이미지 검색어가 본문 검색어와 다르면 별도 임베딩이 추가될 수 있음. 따라서 일반 본문 확장 검색의 캐시 미적중 경로는 최대 4개 본문 벡터와 별도 이미지 검색어 벡터를 준비할 수 있으며, 모든 질문에서 고정 횟수를 쓰는 것은 아님.
- Agent: `aibitat/index.js`의 병원 강제 검색과 `plugins/memory.js` 검색을 거치며, `providers/gemini.js`는 Agent 턴마다 선택 모델을 호출함. 도구 사용 후 재호출할 수 있어 생성 1회 이상으로 변동함. 사전 거절은 0회 가능함. 실제 최대 횟수는 Agent 도구·재시도·추가 검색 설정에 따라 별도 측정해야 함.
- `workspaceThread.js`의 현재 자동 제목 변경은 질문 앞부분을 잘라 저장하므로 이 경로 자체는 Gemini 추가 호출이 아님.
- 모델 이름: 로컬 compose의 답변 기본값은 `gemini-3.8-flash`, 임베딩은 `gemini-embedding-2`임. 운영 환경/작업 공간 설정이 이를 바꿀 수 있으므로 운영 사용 모델로 단정하지 않음.

### 2. schat-safety-evaluator 역할

`safety_evaluator/service.py`의 `/v1/prepare`, `/v1/validate`는 Python 근거·문장 규칙 검사임. `core.py`와 연결된 schat-core 검증 모듈, requirements에서 RAGAS/Gemini 평가 호출 경로를 확인하지 못함. compose도 내부 전용 네트워크로 연결함.

직원 질문에서 안전 게이트가 켜진 경우 Node의 `schatSafety/chat.js`가 이 서비스에 준비·검증을 요청함. 사이에 있는 답변 생성 1회는 **Node의 LLMConnector**가 수행하며 evaluator가 Gemini를 추가 호출하는 구조가 아님. 게이트 적용 여부는 설정에 따라 달라짐.

### 3. Gemini 3.7 Flash와 Embedding 1

- `gemini-3.7-flash`는 확인한 `.env.example`의 Vertex AI 모델 예시 주석에 존재함. 예시는 실제 활성 설정이 아님. 실제 어느 기능에서 사용 중인지 이 자료만으로 확정 불가함.
- “Embedding 1”이 `gemini-embedding-001`을 뜻한다면 Gemini 임베딩 provider의 지원 모델 표에 존재함. 선택 시 검색어·문서 임베딩에 사용하는 공통 엔진이지만, 현재 compose 지정값은 `gemini-embedding-2`임.
- 운영 API 키나 .env를 출력하지 않았음. AI Studio 사용량의 모델별 항목 및 관리자 모델 설정을 받아야 실제 사용 출처를 확정할 수 있음. RAGAS에서 이 모델을 쓴다고 추측하지 않음.

### 4. RPD 초기화 시각

Google 공식 안내는 미국 태평양 시간 자정임. 한국 시간으로 미국 서머타임(PDT) 기간은 오후 4시, 표준시(PST) 기간은 오후 5시임. 2026-10-10은 오후 4시에 해당함. 결제 잔액 충전과 별개이며 한국 자정 초기화가 아님. [공식 제한 안내](https://ai.google.dev/gemini-api/docs/rate-limits)

### 5. RAGAS 대량 평가가 운영 한도를 쓰지 않게 하는 제안

가장 확실한 방법은 별도 Google Cloud **프로젝트**의 평가용 API 키를 평가 실행 환경에서만 사용하고, 생성 모델과 평가용 임베딩 모두 그 프로젝트를 쓰는 것임. 같은 프로젝트에서 키만 새로 발급해도 프로젝트 한도는 분리되지 않음. 평가 입력 답변도 운영 SCHAT API로 생성하면 운영 한도를 쓰므로 격리 테스트 서버/기존 비식별 평가 결과를 사용해야 함. 실제 병원 자료 외부 전송은 별도 승인 필요함. 평가 예산·호출 수·동시 실행 상한을 별도로 두고, 기본 회귀 테스트는 가짜 API로 실행함. 이 제안은 아직 설정에 적용하지 않음.

## 한도를 받은 뒤 조정 방법

모델별로 남은 RPM/질문당 호출 수와 남은 TPM/질문당 총입력 토큰을 계산하고 가장 작은 질문/분 값을 기준으로 함. 응답 시간과 메모리 실측, SDK 재시도 및 문서 처리 등 다른 작업을 고려해 여유를 둠. 질문/분 × 평균 생성시간(초) ÷ 60은 평균 처리 중 수의 참고값이지 최대 동시 정원 보장이 아님. 4단계 부하 테스트로 최종 조정해야 함.

## 최초 중단 시점 기록

구조 조사와 독립 대기열 모듈 구현까지 진행함. 아직 실제 채팅 경로에 연결하지 않았으므로 기능은 미완료이며 제한이 적용되지 않음.

- 새 파일: `server/utils/chatAdmission.js`, `server/__tests__/utils/chatAdmission.node.test.js`.
- 모듈 부재로 테스트가 실패함을 확인한 뒤 구현함. 최종 가짜 시계/가짜 작업 테스트 12개 통과함.
- 확인 범위: 4건 처리·10건 대기, 계정 중복, 순번 갱신, 30초 만료, 생성 120초 만료 시 취소 신호 후 자리 반환, 중복 반환 방지, 취소, 한도 증감, 이전 타이머 제거, 실패 작업의 finally 반환.
- 중요한 제한: 실제 HTTP·Agent의 외부 호출 취소와 화면 표시까지 입증한 테스트가 아님. 모듈의 취소 신호를 모든 실제 실행 경로에 연결하고, 늦게 완료된 검색 뒤 새 생성이 시작되지 않게 해야 함.
- 내부 설정 검증 범위는 동시 처리 1~16 정수임. 관리자 UI/저장소 연동은 아직 없음.
- 실제 API·DB·운영 데이터·Docker를 변경하지 않음. 기능 미완성이므로 stage·commit·push하지 않음.

### 다음 시작 위치

1. HTTP/Agent의 작업 소유권을 연결함. `grepAgents`의 HTTP→WebSocket 전환에서 자리를 조기 반환하지 않도록 하고 미접속·중복 연결도 제한함.
2. 기존 abortSignals와 Agent.abort를 사용해 생성 제한/창 닫기의 실제 호출 중단을 검증함. 이 경계가 통과하기 전에는 제한을 활성화하지 않음.
3. 관리자 설정 저장/현황, 직원 순번, Gemini 혼잡과 별도 오류 표시를 구현함.
4. 통합·회귀·화면 빌드·문서 검증 후, 다른 작업의 미커밋 변경을 제외하고 이 기능만 commit함. push 금지.

## 이어서 구현한 내용

- HTTP 일반 채팅과 Agent WebSocket이 같은 대기열을 사용하도록 연결함. HTTP에서 Agent로 넘기는 준비 단계는 자리를 차지하지 않고, 실제 Agent 연결 때 자리를 얻도록 단순화함. 따라서 WebSocket에 접속하지 않은 요청이 처리 자리를 차지하지 않음. 같은 invocation의 중복 연결은 거절함.
- 대기 순번은 HTTP/SSE와 WebSocket 양쪽에서 직원 화면에 전달함. 입장 후 준비 표시를 유지하며 질문·답변의 저장 번호가 대기 안내 항목으로 잘못 연결되지 않도록 보완함.
- 관리자 → 시스템 상태에 현재 처리/대기 수와 최대 동시 답변 수 설정을 추가함. 기본 4건, 허용 범위 1~16임. 숫자를 낮춰도 이미 진행 중인 답변은 강제로 끊지 않음.
- 기존 system_settings에 한도만 저장함. DB 구조 변경 없음. 재시작 시 설정은 다시 읽되 이전 처리/대기 숫자는 복원하지 않음. 설정 읽기 실패는 조용히 무시하지 않고 요청 오류로 처리함.
- 창 닫기와 120초 만료 시 Agent 및 Gemini 답변/검색 임베딩 SDK에 취소 신호를 전달함. 취소된 검색이 늦게 끝나도 답변 생성을 새로 시작하지 않도록 확인함. /img 명령도 기존 취소 인자를 사용해 공통 제한에 포함하며 /reset은 기존 즉시 처리 유지함.
- 검색 비율·검색어·Top-K·모델·프롬프트를 바꾸지 않음. 임베딩 코드에 추가한 내용은 취소 신호 연결뿐임. 기존 체크리스트·문서 업데이트·동의어 등 타 작업은 커밋 대상에서 제외함.

### 검증

- 신규 대기열/실제 HTTP·Agent 연결/설정·권한/검색 임베딩 취소 테스트 및 기존 검색·대기표시·채팅 중단 회귀 테스트 합계 46개 통과함.
- 처음 Agent 준비 도중 닫기 테스트가 실패했으며, 조기 자리 반환이 취소 리스너를 제거하는 원인을 수정한 후 통과함.
- 코드 검토에서 찾은 임베딩 취소 누락과 질문 저장 번호 연결 및 입장 직후 준비 표시 문제를 보완하고 회귀 테스트에 추가함.
- Vite production build 및 postbuild 통과함. 기존 브라우저 호환 목록 갱신 안내·청크 크기 등 경고가 있음. 화면 이벤트 테스트에는 기존 import.meta/CJS 경고가 있음.
- 문서 화면을 재생성하고 분리 검사 11개 통과함. 기존 생성 스크립트의 escape sequence 경고가 있음.
- 실제 Gemini 호출·운영 DB·Chroma·Docker 재빌드·운영 서버 접속은 하지 않음. 실제 브라우저/여러 직원 동시 사용 부하 시험은 미실시임.

### 적용 범위와 제한

- 한 Node 서버 프로세스의 직원 웹 채팅 제한임. 서버 프로세스를 여러 개로 늘리면 공통 저장소를 사용하는 대기열로 바꿔야 함.
- API 키용 별도 AnythingLLM 개발자 API, 모바일 전용 경로, 예약 작업·문서 등록·퀴즈·동의어 생성의 전체 호출을 통합 제한하는 기능은 아님. 직원 웹 채팅 주소에 직접 요청해도 인증된 사용자 ID 기준 제한은 적용됨.
- 처리 시간에는 검색과 Agent 세션의 추가 입력 대기도 포함됨. 서버 120초 상한과 별개로 기존 직원 화면의 70초 자동 중단 동작은 유지함. 대기열 화면에서는 이 자동 중단 컴포넌트를 표시하지 않지만 입장 후 기존 질문 시작 시각 기준의 중단이 더 먼저 적용될 수 있음.
- API 취소는 추가 대기를 중단하는 신호이며 이미 발생한 Gemini 비용을 취소하는 기능은 아님. 중단 시점의 로컬 검색 계산이 즉시 종료됨을 보장하지 않음.
- 초기값 4건은 안전 인원 인증이 아님. 위 RPM/TPM 계산과 별도 부하 테스트로 조정해야 함.

### 사용자가 확인할 순서

1. 이 변경이 로컬 실행 환경에 반영된 뒤 관리자 → 시스템 상태에서 동시 답변 수와 현재 처리/대기 수를 확인함. 이번 작업에서 Docker에는 반영하지 않았음.
2. 실제 API 비용 없이 자동 테스트를 실행하려면 Node로 `--test server/__tests__/utils/chatAdmission*.node.test.js frontend/src/utils/chatAdmissionDisplay.node.test.mjs`를 실행함. 이 테스트는 실제 Gemini와 운영 DB를 호출하지 않음.
3. 별도 테스트 환경에서 최대 동시 수를 1로 저장하고, 서로 다른 두 테스트 계정으로 가짜 답변 호출을 진행하면 두 번째 계정에 1번째 대기 안내가 보여야 함. 같은 계정의 다른 탭은 중복 안내가 보여야 함.
4. 첫 창을 닫으면 대기하던 질문이 입장하고, 종료 후 처리/대기 수가 0으로 돌아와야 함. 설정은 확인 후 4로 복원함. 가짜 응답 환경이 없는 실제 3001에서 질문하면 Gemini 비용이 발생할 수 있으므로 이번에는 실행하지 않음.

커밋에는 이 기능의 코드·테스트·기록만 선별함. 다른 작업이 함께 반영된 생성 문서 화면은 로컬 갱신하되 통째로 이 기능 커밋에 넣지 않음. push하지 않음.
현재 상태 문서도 이번 기능 설명 한 항목만 선별함. 기존 pre-commit은 작업공간 전체에서 생성 화면을 만들어 자동 stage하므로, 이번 선별 커밋에서는 해당 자동 stage를 실행하지 않고 이미 수행한 문서 생성/분리 검사 결과를 사용함. Git 설정 자체는 변경하지 않음.
