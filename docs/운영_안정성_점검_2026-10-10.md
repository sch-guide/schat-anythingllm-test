# SCHAT 운영 안정성 점검 보고서

점검일: 2026-10-10

## 먼저 읽을 결론

1. **후속 사용자 서버 점검에서 주원인을 Docker Build Cache 21GB(87개) 누적으로 확인함.** Images 6.9GB, storage 1.4GB이며 로그·백업은 작았다고 전달받음. AI가 서버에 직접 접속한 결과는 아님.
2. 코드에서 우선 확인할 위험은 **Docker 로그 제한 미지정, 일반 업로드 용량 제한 부족, 매우 긴 질문의 명시적 길이 제한 부족, 채팅 공통 대기열 부재**임.
3. 원본 PDF·이전 문서·DB·Chroma는 단순 임시 파일이 아님. 오래됐다는 이유만으로 삭제하면 안 됨.
4. “혼잡합니다”는 직원 수가 일정 수를 넘었다는 뜻이 아니라, **Gemini가 호출 제한 오류를 돌려줬다는 뜻**임.
5. 지금 자료만으로 “동시에 몇 명까지 안전함”을 확정할 수 없음. VM 사양, AI Studio 한도, 질문당 사용량, 응답 시간을 함께 확인해야 함.

### 점검 범위와 한계

후속 사용자 확인 사양은 CPU 2개, 메모리 3.8GB, 스왑 **사용량** 1.3GB임. Docker 이미지·캐시는 공유 공간이 있어 단순 합산하지 않음. 스왑 사용만으로 현재 장애라고 단정하지 않으며 응답 지연과 지속적인 스왑 입출력을 별도 확인해야 함.

후속 조치로 배포 안내에 빌드 성공·서비스 확인 후 `sudo docker builder prune -f`를 추가하고 [5GB 기준 자동 관리 안내](Docker_빌드캐시_자동관리.md)를 작성함. DB·Chroma volume은 삭제하지 않음. **서버 정리 실행·회수량·자동 설정 적용은 아직 미확인**임. 아래 서버 미확인 설명은 최초 코드 점검 범위이며 사용자 측정 결과로 확인된 부분만 보완함.

- 현재 Git 저장소의 로컬 코드와 설정을 읽기 전용으로 점검함. 기준 HEAD는 `e09f362c`이며 미커밋 변경도 존재함. 이 번호만으로 미커밋 코드를 재현할 수는 없음.
- 현재 작업 위치는 `docs_view`이나 Git에서 확인한 저장소 루트의 `server`, `frontend`, `collector`, `docker`를 조사함. 다른 프로젝트의 평가 결과는 합치지 않음.
- 이 보고서는 로컬 구현 점검임. Google Cloud에 같은 코드가 배포됐거나 실제 운영에서 통과했다는 인증이 아님.
- `.env` 값, API 키, 직원 정보, 병원 원문 전체는 보고서에 넣지 않음.
- 코드·설정·DB 변경, 삭제, 서버 접속, 실제 Gemini 호출, Docker 재빌드, commit/push/tag는 하지 않음. 요청에 따라 보고서만 추가하며 문서 화면은 재생성하지 않음.

## 1. 저장공간 점검

### 1-1. 서버에서 직접 실행할 조회 명령

아래는 **Google Cloud SSH 창의 Linux 명령**임. Windows PowerShell에서 실행하는 명령이 아님. 삭제·정리 명령은 포함하지 않았음. 큰 폴더를 읽는 작업은 디스크에 잠시 부담을 줄 수 있으므로 한 줄씩 실행하고, 이용이 적은 시간에 확인하는 것이 좋음.

#### ① 디스크가 실제로 얼마나 찼는지

```bash
df -hT
df -ih
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS
```

- `df -hT`: 실제 사용 가능한 공간과 사용률임.
- `df -ih`: 용량 대신 파일 개수 한도가 찼는지 확인함.
- `lsblk`: 디스크 자체 크기와 연결 위치임. 디스크는 40GB인데 파일시스템은 여전히 약 30GB라면 확장 반영 여부를 별도로 확인해야 함. 여기서는 확장 명령을 실행하지 않음.

#### ② 큰 폴더부터 찾기

```bash
sudo du -xhd1 / 2>/dev/null | sort -hr
sudo du -xhd1 /var 2>/dev/null | sort -hr
sudo du -xhd1 /var/lib 2>/dev/null | sort -hr
du -xhd1 "$HOME" 2>/dev/null | sort -hr
du -xhd1 "$HOME/schat-anythingllm-test" 2>/dev/null | sort -hr
du -xhd1 "$HOME/schat-anythingllm-test/server/storage" 2>/dev/null | sort -hr
du -xhd1 "$HOME/schat-anythingllm-test/collector" 2>/dev/null | sort -hr
du -xhd1 "$HOME/backup" 2>/dev/null | sort -hr
```

위쪽에 나오는 폴더가 큰 폴더임. 첫 줄은 해당 폴더 전체 합계일 수 있음. `-x`는 다른 디스크로 넘어가지 않는 옵션이므로 별도 디스크가 있으면 그 연결 위치도 따로 조사해야 함. 없는 경로는 출력되지 않을 수 있음.

#### ③ Docker가 차지하는 부분 구분

```bash
sudo docker system df -v
sudo docker ps -a --size
sudo docker info --format 'DockerRoot={{.DockerRootDir}} LogDriver={{.LoggingDriver}}'
sudo docker inspect --format '{{.Name}} {{json .HostConfig.LogConfig}}' schat-web schat-chromadb schat-safety-evaluator
sudo docker inspect --format '{{.Name}} LogPath={{.LogPath}}' schat-web schat-chromadb schat-safety-evaluator
```

- 이미지: 프로그램 실행에 필요한 큰 묶음 파일임. 이전 배포 이미지가 남을 수 있음.
- Build Cache: 다음 빌드를 빠르게 하려고 남기는 자료임.
- Volume: DB·검색 자료가 있을 수 있는 보관소임. **미사용으로 보여도 바로 삭제하면 안 됨.**
- `RECLAIMABLE`은 Docker 관점의 회수 가능 표시이지 업무상 삭제 승인 표시가 아님.
- 컨테이너 크기에는 별도 연결된 storage·volume 전체 용량이 포함되지 않으므로 위 결과를 단순 합산하지 않음.
- `LogConfig`에서 로그 종류와 `max-size`, `max-file`을 확인함. 기본 경로가 `/var/lib/docker`라면 다음 조회로 내부 큰 항목을 확인할 수 있음. 다른 경로가 나오면 그 경로를 사용해야 함.

```bash
sudo du -xhd1 /var/lib/docker 2>/dev/null | sort -hr
sudo du -xhd1 /var/lib/docker/containers 2>/dev/null | sort -hr
sudo journalctl --disk-usage
du -h "$HOME/build.log" 2>/dev/null
```

로그 원문, `.env`, 전체 `docker inspect`, `docker compose config` 출력은 키나 내부 정보가 섞일 수 있으므로 공유하지 않음. 위 명령은 필요한 설정 필드만 출력하도록 제한함. Docker 내부 로그 파일을 직접 지우거나 비우지 않음.

### 1-2. 코드에서 확인한 누적 위치

| 대상 | 위치/저장 방식 | 자동 정리·제한 확인 | 판단 |
| --- | --- | --- | --- |
| 서버 실행 로그 | `server/utils/logger/index.js`에서 Console로 출력 → Docker 로그 드라이버가 보관 | 로거 자체 파일 회전 없음. 현재 compose에도 크기·개수 제한 없음. VM 공통 설정은 미확인 | 우선 측정 대상 |
| Chroma 및 다른 컨테이너 로그 | 각 컨테이너 표준 출력 | compose의 로그 제한 없음. 드라이버 실제 설정은 서버에서 확인 필요 | 반복 오류 시 증가 가능 |
| 관리자 시스템 기록 | `server/models/eventLogs.js`의 DB `event_logs` | 삭제 함수와 관리자 삭제 경로는 있으나 확인한 경로에 기간별 자동 만료 없음 | 사용·오류 이벤트에 따라 DB 증가 |
| 대화·통계 데이터 | DB의 대화 기록, 사용량 기록 | 이번 점검에서 공통 기간별 자동 삭제 정책을 확인하지 못함 | 업무 기록이므로 임의 삭제 금지 |
| 원본 PDF | 기본 `server/storage/original-documents` | 보존 목적. PDF와 연결 정보 및 `.pdf-ref-secret` 존재 | 원본 보기와 과거 출처에 필요 |
| 문서 이미지 | `server/storage/document-images` 계열 | 일괄 기간 만료 정책은 확인하지 못함 | 원문 이미지 기능에 사용될 수 있음 |
| 문서 업데이트 보관 | `server/storage/document-updates/<작업번호>` 및 기존 문서 자료 | 로컬 `documentUpdates/service.js`는 원본과 작업 기록 영구 보관 의도를 명시함 | 이전 버전·복구 기록 누적 가능. 단순 임시 파일 아님 |
| 검색용 문서/임베딩 캐시 | storage의 문서 자료, 검색 캐시 및 Chroma volume | 캐시는 이름만으로 삭제 안전성을 판단할 수 없음 | 재처리·비용·검색 장애 가능 |
| 업로드 대기/처리 산출물 | `collector/hotdir`, `collector/outputs`, 원본 PDF의 `.incoming` | 일부 경로에 처리 후 정리 코드 있음. 모든 실패·강제 종료 뒤 정리는 보장하지 못함 | 오래된 잔여물 조사 후보 |
| 진단/정리 기록 | `server/storage/schat-diagnostics/storage-cleanup` 등 | 정리 작업 명세를 저장함. 조사한 코드에 전체 보관량 상한 없음 | 원인 조사 기록이므로 확인 후 보관 정책 필요 |
| Docker 이미지·빌드 캐시 | Docker 관리 영역 | compose 실행만으로 모든 이전 이미지/캐시가 정리되는 구조는 아님 | 재빌드가 반복되면 증가 가능 |
| DB 백업 | 사용자 배포 절차의 `~/backup` | 날짜별 복사본 자동 보관 기한은 확인되지 않음 | 백업 횟수만큼 증가 가능 |
| 빌드 로그 | 사용자 배포 절차의 `~/build.log` | 기존 명령의 `>`는 실행 시 파일을 새로 쓰지만 실행 중 크기 제한은 없음 | 크기 확인 필요 |

Docker의 `json-file` 방식은 `max-size` 미설정 시 기본 크기 제한이 없음. 단, 이 서버가 실제로 그 기본 설정을 사용하는지는 위 `LogConfig`로 확인해야 함. [Docker 공식 로그 설명](https://docs.docker.com/engine/logging/drivers/json-file/)

**“얼마나 쌓이는가”의 정확한 GB/일 값은 코드만으로 알 수 없음.** 질문 수, 오류 반복, PDF 페이지 수, 업데이트 횟수에 따라 달라짐. 같은 시간에 위 조회를 이틀 이상 반복해 증가량을 비교해야 함. 예를 들어 하루 0.5GB씩 증가한다면 추가한 10GB는 대략 20일분일 뿐임. 이는 계산 예시이며 SCHAT 실측값이 아님.

### 1-3. 이미 있는 자동 정리 기능

`server/utils/BackgroundWorkers/index.js`와 `server/utils/boot/index.js`에서 서버 시작 시 예약되는 작업을 확인함.

| 작업 | 코드상 주기 | 대상과 보호 조건 |
| --- | --- | --- |
| `cleanup-orphan-documents` | 12시간 | 직접 채팅 첨부 저장소에서 `WorkspaceParsedFiles`에 없는 파일을 정리함. 일반 등록 지침 전체 정리가 아님 |
| `cleanup-generated-files` | 8시간 | AI 생성 파일 중 사용 참조와 나이 등을 확인함. 정상 형식 자료는 최소 1시간 조건이 있으며, 형식에 맞지 않는 파일/폴더 처리도 포함함 |
| `cleanup-generated-images` | 9시간 | 생성 이미지의 대화/예약 작업 참조와 최소 1시간 조건 등을 확인함 |

따라서 “자동 정리가 전혀 없다”도, “storage가 모두 알아서 정리된다”도 맞지 않음. 서버에서 예약 작업이 실제 성공했는지는 이번에 확인하지 않았음. `storageCleanup.js`는 참조를 확인하는 별도 정리 기능이며, 디스크 전체 자동 청소기로 간주하면 안 됨.

### 1-4. 지워도 되는 것과 지우면 안 되는 것

이번 보고서에서 **즉시 삭제를 승인하는 파일은 없음**.

| 구분 | 대상 | 조건/이유 |
| --- | --- | --- |
| 조건 확인 후 정리 가능 후보 | 사용하지 않는 빌드 캐시 | 다음 빌드가 느려질 수 있음. 실제 미사용 여부 확인 필요 |
| 조건 확인 후 정리 가능 후보 | 이전 Docker 이미지 | 현재 실행 이미지와 되돌리기용 이미지는 보존해야 함 |
| 조건 확인 후 정리 가능 후보 | 오래된 실행 로그 | 장애 조사에 필요한 기간 보관 후 Docker의 정식 회전 정책으로 관리. 내부 파일 수동 삭제 금지 |
| 확인 필요 | 오래된 업로드 임시물·처리 산출물 | 현재 처리 중인지, DB/출처 참조가 있는지, 재시도에 필요한지 먼저 확인 |
| 확인 필요 | 오래된 백업·진단 자료 | 복구 가능한 최신 백업과 보관 기준을 먼저 확보 |
| 삭제 금지 | `anythingllm.db` 및 SQLite 관련 파일 | 직원·대화·설정 등 데이터 손상 가능 |
| 삭제 금지 | Chroma volume 및 검색 저장소 | 문서 검색 불가·재색인 필요 가능 |
| 삭제 금지 | 원본 PDF·문서 이미지·이전 문서·업데이트 기록 | 과거 Citation, 체크리스트, 퀴즈 및 복구 연결 가능 |
| 삭제 금지 | 체크리스트 JSON, `.env`, 키·암호화 파일 | 실제 운영 상태와 인증·원문 연결 유지에 필요 |

워크스페이스 삭제는 용량 청소나 시범 운영 통계 구분 수단으로 사용하지 않는 것이 안전함.

## 2. 동시접속 점검

### 2-1. 모델 이름: 기본 설정과 실제 운영값 구분

| 항목 | 로컬 코드/compose에 확인된 값 | 실제 서버에서 추가 확인할 것 |
| --- | --- | --- |
| Gemini 답변 모델 | `GEMINI_LLM_MODEL_PREF` 기본값 `gemini-3.8-flash` | 환경 설정 및 작업 공간별 모델 지정에 따라 다를 수 있음 |
| 임베딩 모델 | compose `EMBEDDING_MODEL_PREF=gemini-embedding-2`, Gemini 임베딩 코드의 기본값도 같음 | 실제 배포 compose와 관리자 연결 설정 확인 |
| 공급자 | compose `LLM_PROVIDER=gemini`, `EMBEDDING_ENGINE=gemini` | Google Cloud 실행 컨테이너가 해당 버전인지 확인 |

근거: `docker/docker-compose.yml`, `server/utils/EmbeddingEngines/gemini/index.js`, `server/utils/AiProviders/gemini/index.js`, `server/utils/agents/aibitat/providers/gemini.js`.

관리자 시스템 연결/답변 설정에서 모델 이름을 먼저 확인함. 비밀 키를 복사하지 않음. 위 표는 현재 VM에서 모델 호출 성공을 확인한 결과가 아니라 **현재 로컬 설정에 적힌 값**임.

### 2-2. AI Studio에서 내 한도 확인

1. SCHAT의 API 키를 발급한 Google 계정으로 AI Studio에 로그인함.
2. SCHAT 키가 속한 **같은 Google Cloud 프로젝트**를 선택함. 다른 프로젝트의 한도를 보면 안 됨.
3. [AI Studio 요청 제한 화면](https://aistudio.google.com/rate-limit?timeRange=last-28-days)을 엶. 화면 이름은 Rate limits 또는 사용량/요청 제한으로 표시될 수 있음.
4. 실제 답변 모델과 임베딩 모델을 각각 찾아 아래 항목을 기록함.
5. Projects 화면의 결제 등급도 확인함. 메뉴가 달라졌으면 [공식 안내의 View your active rate limits 링크](https://ai.google.dev/gemini-api/docs/rate-limits)를 이용함.

| 기록할 항목 | 쉬운 뜻 |
| --- | --- |
| RPM | 1분 동안 보낼 수 있는 요청 수 |
| TPM | 1분 동안 보낼 수 있는 입력 토큰 양. 긴 지침을 함께 보내면 빨리 차게 됨 |
| RPD | 하루 요청 수 한도 |
| 추가 표시되는 제한 | 모델별 별도 제한, 단기간 지출 제한 등이 있다면 함께 기록 |
| Tier | 현재 프로젝트의 이용 등급 |

한도는 키 하나가 아니라 **프로젝트 단위**이며 모델과 등급에 따라 다름. 하루 한도 초기화는 한국 자정과 다를 수 있음. 공식 한도도 실제 처리 용량을 보장하는 숫자는 아님. [Google 공식 요청 제한 설명](https://ai.google.dev/gemini-api/docs/rate-limits)

### 2-3. VM CPU·메모리와 현재 부하 확인

```bash
nproc
lscpu
free -h
df -hT
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS
uptime
sudo docker stats --no-stream
sudo docker inspect --format '{{.Name}} OOMKilled={{.State.OOMKilled}} RestartCount={{.RestartCount}} MemoryLimit={{.HostConfig.Memory}} NanoCpus={{.HostConfig.NanoCpus}}' schat-web schat-chromadb schat-safety-evaluator
```

- CPU: 동시에 계산하는 능력임. 메모리: 잠시 펼쳐 놓을 수 있는 자료량임. 디스크: 장기 보관함임.
- 디스크를 30→40GB로 늘려도 CPU·메모리·Gemini 한도는 자동 증가하지 않음.
- 현재 compose에 명시적인 CPU/메모리 상한은 확인되지 않음. 컨테이너 제한이 0이면 보통 별도 상한 미지정이지 메모리가 무한하다는 뜻이 아님.
- `OOMKilled=true`는 메모리 부족으로 종료된 흔적임. false여도 과거 모든 메모리 문제가 없었다는 증명은 아님.

### 2-5. “혼잡” 안내가 뜨는 실제 조건

현재 로컬 `server/utils/geminiAvailability.js`의 분류를 확인함.

- 우선 HTTP 402/429 또는 `RESOURCE_EXHAUSTED` 계열인지 확인함.
- 일일·월간 한도, 크레딧/잔액 소진을 뜻하는 정보는 한도 소진으로 분류함.
- 분당/순간 제한과 불명확한 429 등 제한 오류는 혼잡으로 처리함. 429만으로 돈이 다 떨어졌다고 단정하지 않음.
- 그 밖의 오류는 일반 오류 안내임.
- 혼잡 문구: “사용자가 많아 잠시 후 다시 시도해 주세요.”

이 문구는 **직원 수를 직접 센 결과가 아님.** 다른 Gemini 작업과의 한도 공유, 질문에 포함된 긴 지침, 순간 요청 몰림 때문에 직원이 적어도 나타날 수 있음. 로컬 알림 코드가 현재 Docker/VM에 반영됐는지는 별도 확인 필요함.

### 2-6. 최대 동시 처리 인원 추정 방법

VM 사양은 후속 사용자 보고로 확인됐으나 모델별 실제 한도·질문당 토큰·처리 시간이 없어 인원 수는 여전히 **계산 불가**임.

1. AI Studio에서 답변·임베딩 모델의 RPM/TPM/RPD를 기록함.
2. 일반 질문 한 건이 실제로 Gemini를 몇 번 호출하는지 확인함. Agent 재호출 등이 있으면 질문 1건 = 호출 1건이 아님.
3. 채팅 기록에서 질문당 입력 토큰과 응답 시간을 확인함. 평균뿐 아니라 오래 걸리는 질문도 확인함.
4. 문서 등록·이미지 설명·퀴즈·동의어 생성 등 같은 프로젝트 사용량을 제외해 여유를 남김.
5. 아래 각 기준 중 가장 작은 값이 1분 처리량의 출발점임. 그보다 여유 있게 계획하고 VM 부하와 오류율을 확인함.

```text
요청 수 기준 질문/분 = 남은 모델 RPM ÷ 질문당 모델 호출 횟수
입력량 기준 질문/분 = 남은 모델 TPM ÷ 질문당 전체 입력 토큰
임베딩 기준도 같은 방식으로 계산
예상 동시 답변 처리 수 ≈ 질문/분 × 평균 답변 시간(초) ÷ 60
```

예를 들어 모든 제약을 고려해 분당 12문항이 가능하고 답변이 평균 10초라면, 평균적으로 약 2건이 처리 중이라는 계산임. **이는 예시이며 SCHAT 정원 2명이라는 뜻이 아님.** 로그인한 직원 수와 동시에 질문한 직원 수는 다름. 20명이 동시에 누르는 순간 몰림도 이 평균식만으로 보장할 수 없음.

실측 부하 테스트와 실제 API 호출은 이번에 하지 않았음. 추후 별도 승인 후 테스트 문서·가짜 API로 먼저 확인하고, 비용을 정한 소규모 실제 호출을 검토하는 순서가 안전함.

## 4. 추천하는 다음 순서 — 이번에는 실행하지 않음

1. 서버에서 1-1과 2-3의 조회 명령을 실행하고, **용량·모델 이름·한도·CPU·메모리 숫자만** 확인함. 파일명에 개인정보가 있다면 공유 전에 가림.
2. 주원인은 사용자 측정상 빌드 캐시였음. 배포 후 캐시 정리와 자동 관리 적용 후 회수량·남은 공간을 확인해야 함. 아직 실행 완료로 기록하지 않음.
3. 다중 사용자 모드와 관리자 권한 차단이 실제 서버에서도 동작하는지 확인함.
4. 별도 개선 작업에서 일반 업로드/질문 길이 제한과 공통 호출 대기열을 검토함. 이번 보고서로 자동 승인하거나 코드를 바꾸지 않음.
5. 로그 보관량·백업 보관 기간은 먼저 합의함. 원본 PDF·이전 문서·Chroma를 먼저 지우는 방식은 피함.
