# release-1 운영 반영 확인 순서

이 문서는 나중에 사용자가 직접 진행할 배포 안내임. 이번 작업에서는 GitHub push, Google Cloud 접속, 운영 반영을 하지 않음. 최종 문서 업데이트 검증·커밋 완료 여부는 해당 작업일지를 확인해야 함.

## 이전 1차 안내와 다른 점

- `81ffe720`까지만 반영하는 1차 안내와 현재 release-1 준비 범위는 다름.
- 현재 준비 범위에는 개인 체크·메모 DB 변경 1개와 동의어 후보 DB 변경 2개가 포함됨. 기존 운영 기준 `b5aa77bd`와 비교한 결과이며, 실제 서버 현재 커밋을 기준으로 다시 확인해야 함.
- 시험용 계정·PDF·DB·preview-storage를 운영으로 복사하지 않음. 실제 서버의 `.env`, storage, Chroma volume은 유지함.
- DB 변경은 기존 자료를 지우는 초기화 명령이 아님. `prisma migrate reset`, `docker compose down -v`는 실행하지 않음.

## 순서

1. **스냅샷과 백업**: 이용이 적은 시간에 질문·업로드·관리자 수정 작업을 멈추고, 복원 가능한 VM 스냅샷을 확보함. DB·storage·Chroma가 서로 맞는 시점의 백업이어야 함. 실행 중 SQLite 파일 하나만 복사하지 않고 온라인 백업 또는 정상 종료 후 일관된 백업을 사용함.
2. **현재 버전 기록**: 서버 저장소에서 `git rev-parse HEAD`, `git status --short`를 확인하고 현재 이미지·컨테이너 구성도 기록함. 기존 수정사항이 있으면 강제 덮어쓰기하지 않음. 키가 들어갈 수 있는 전체 환경설정 출력은 공유하지 않음.
3. **코드 받기**: 별도 push 승인과 GitHub 반영 후, 검증한 정확한 release 커밋을 받음. 단순히 최신 main을 받으면 이후 작업까지 포함될 수 있음. 운영 현재 커밋과 목표 커밋 사이의 migration·storage 변경을 확인함. 기존 추적 storage 정리는 이번 기능과 별개이며 함께 진행하지 않음.
4. **DB 변경 확인**: 목표 버전의 migration 목록과 현재 적용 상태를 확인함. 현재 Docker 시작 스크립트는 새 이미지가 시작될 때 `prisma generate` 다음 `prisma migrate deploy`를 실행하고 성공해야 서버를 시작함. 따라서 실제 적용 시점은 다음 빌드·실행 단계임. 따로 적용할 경우에도 반드시 목표 이미지와 기존 배포 설정을 사용하고, 중복 실행·reset을 하지 않음.
5. **빌드·실행**: 기존 운영 compose·환경설정·데이터 연결을 그대로 유지해 목표 버전을 빌드하고 실행함. 로컬 시험용 포트·폴더·컨테이너는 운영 설정으로 가져가지 않음. migration 실패 또는 복구 확인 필요 상태면 임의 파일 삭제로 해결하지 않음.
6. **확인**: 로그인, 직원 질문·출처 원문, 체크리스트·퀴즈, 관리자 예산·동의어·답변 재사용을 확인함. 문서 교체는 실제 지침 대신 테스트 자료로 먼저 확인하고 구본이 검색에 남지 않는지, 구본 원본과 과거 연결이 유지되는지 확인함. 개인 메모는 본인 계정만 조회되는지 확인함.
7. **빌드 캐시 정리**: 새 서비스가 정상이고 다른 빌드가 없는 것을 확인한 뒤 아래 명령만 실행함.

```bash
sudo docker builder prune -f
sudo docker system df
df -h
```

DB·Chroma volume·server/storage·이전 원본을 삭제하지 않음. `docker volume prune`, `docker compose down -v`, 전체 정리용 `docker system prune`으로 대체하지 않음.

8. **문제 시 되돌리기**: 추가 업로드와 변경을 중단하고 기록한 이전 버전과 백업을 확인함. 새 DB 구조에 이전 코드를 무작정 연결하지 않음. 스냅샷/DB/storage/Chroma를 일관된 시점으로 복구하면 배포 후 새 기록이 사라질 수 있으므로, 먼저 그 기록의 보존 여부를 결정해야 함. 이 데이터 손실 결정은 자동 실행하지 않음.

## 문서 업데이트 직접 확인

새 코드가 반영된 별도 시험 환경에서 관리자 자료 등록 화면을 엶. 현재 3001·3002·3003은 재시작하지 않았으므로 최신 기능이 보인다고 보장하지 않음.

이번 교체 기능은 Linux Docker의 PDF와 Chroma, 단일 앱 서버를 대상으로 함. 여러 부서가 함께 쓰는 문서·자동 감시 문서·부서에 연결되지 않은 구본은 안전상 교체를 중단하며 무리하게 삭제하지 않음. 준비 자료와 문서 저장소는 같은 파일시스템이어야 함. 새 DB migration은 추가하지 않음. Windows 직접 서버 실행의 모든 복구 경계까지 검증한 것은 아님.

서버가 중단되면 다음 시작 및 주기적 확인에서 미완료 작업을 복구함. 자료와 잠금 소유권을 확인할 수 없으면 임의로 지우지 않고 확인 필요 상태로 남김. 복구 기록·잠금 파일을 수동으로 지우지 않음. 원본 PDF·구본·작업 기록은 계속 보관되므로 저장공간은 별도로 점검함.

1. 개인정보 없는 같은 이름의 시험 PDF 두 판본을 준비함. 구본 등록 뒤 신본과 다른 신규 파일을 같이 선택하여 확인 팝업에서 취소함. 두 파일 모두 새로 등록되지 않아야 함.
2. 같은 묶음을 다시 선택해 업데이트함. 구본 원본·과거 연결은 유지되고, 검색 자료는 신본으로 바뀌며 연결된 항목 목록이 보여야 함.
3. 교체 중 다른 창에서 같은 자료 삭제·해당 부서 초기화를 시도하면 안내로 막혀야 함. 다른 부서 질문은 계속 가능해야 함. 실제 지침이나 운영 자료로 장애·강제 종료 시험을 하지 않음.
