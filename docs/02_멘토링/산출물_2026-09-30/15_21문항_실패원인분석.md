# SCHAT 21문항 실패 원인 분석

> 이 문서는 A8 검색 재평가에서는 정답 쪽을 찾았지만 Automatic 답변·출처에서 실패한 이유를 분석한 기록입니다. 검색·답변·Citation 코드는 수정하지 않았고, 2026-09-29에 저장한 실제 실행 결과와 당시 로그, 현재 코드를 비교했습니다.

## 1. 결론부터 보기

이번 문제는 **A8의 Top-10 검색 정확도와 Automatic이 실제 Gemini에 넘기는 근거가 서로 다른 단계의 결과**라는 데서 시작했습니다.

- A8은 이미지 설명을 제외한 본문 벡터 654개에서 Vector/BM25/Hybrid **상위 10개**에 정답 문서·쪽이 있는지 측정합니다.
- 실제 Automatic은 상위 후보를 만든 뒤 `약한 근거 제거 → 질문 의도 필터 → 일반 질문 최대 4개/절차 질문 최대 6개` 과정을 거칩니다.
- 따라서 A8에서 정답 쪽을 찾았어도, 실제 답변 직전에는 0개가 될 수 있습니다.
- 부적합 4건 중 S04·S12·T16은 이 후단 선택에서 0개가 되었고, S11은 정답 본문 대신 p.75 이미지 설명 1개만 남았습니다.
- S06·T15는 구어체 질문이 병원 문서 질문으로 감지되지 않아 선행 검색이 실행되지 않았습니다. 저장된 `response.sources`도 처음부터 0개였으므로 frontend Citation 문제가 아닙니다.
- Citation 과다는 모든 검색 호출의 source를 누적 저장하는 구조와, “실제로 답변에 사용한 source ID”를 Gemini가 돌려주지 않는 구조가 함께 만든 문제입니다.
- 추가 rag-memory는 부적합 4건에는 발생하지 않았습니다. 실패 원인은 추가 검색이 아니라 **첫 검색의 근거 선택**입니다. 다만 S08·S09·T17에서는 추가 검색이 각각 3·1·2회 발생해 저장 source 수를 늘렸습니다.

## 3. A8과 Automatic의 경로 차이

| 단계 | A8 재평가 | 실제 Automatic |
|---|---|---|
| 입력 | 원 질문 | 원 질문 |
| 질문 임베딩 | Gemini embedding | Gemini embedding |
| Vector 후보 | 본문 벡터 순위 | 본문과 image_description을 포함한 Chroma 후보 |
| BM25 | 단어 순위 | 활성 동의어·띄어쓰기 보완을 포함한 운영 BM25 |
| Hybrid | 75:25 순위 Top-10 평가 | 75:25 결합 후 운영 필터 적용 |
| 후단 필터 | 없음 | 약한 꼬리 제거, 의도·초점 필터, 비답변 자료 제외 |
| 최종 개수 | 10개를 평가 | 일반 4개, 절차형 최대 6개 |
| 용도 | 정답 쪽 recall 평가 | Gemini context와 Citation source 생성 |

핵심 코드는 다음과 같습니다.

- `schatBm25.js`의 `filterWeakHybridTail`: BM25 내용 단어 일치율이 2/3 이상이면 유지합니다. 그보다 낮으면 보통 Vector 유사도 0.70 이상이어야 합니다.
- `schatBm25.js`의 `filterIntentFocusedCandidates`: 질문 의도와 근거의 항목 성격을 다시 확인합니다.
- `chroma/index.js`의 `evidenceResultLimit`: 일반 질문은 workspace Top-N, 절차 질문은 최대 6개로 제한합니다.
- `memory.js`: 이 최종 source만 context로 만들고 Citation 보관소에 넣습니다.

즉 A8 100%는 거짓 결과가 아니라 **후보 회수 능력**을 뜻합니다. 실제 답변 성공률까지 뜻하지는 않습니다.

### UAT-S04 — “진정할 때 주의할 점은?”

- 운영 토큰 정리는 `진정할`, `주의할`처럼 활용형을 그대로 남깁니다. 현재 동작은 `진정`, `주의`로 줄이지 않습니다.
- 따라서 질문 의도 `주의사항`도 감지되지 않고, 문서에 있는 `진정`, `주의`와 BM25 내용 일치율도 낮아집니다.
- A8 Vector 유사도는 p.166 0.66861, p.162 0.65719, p.163 0.65670, p.159 0.65617이었습니다. 순위는 좋지만 운영의 독립 Vector 유지 기준 0.70보다 낮습니다.
- 당시 Automatic 로그의 첫 검색 선택 수는 0개였습니다. 추가 rag-memory 호출도 없었습니다.
- 따라서 Gemini는 정답 근거를 받고도 무시한 것이 아니라, `등록된 병원 문서에서 근거를 찾지 못했으며 일반 지식으로 보완하지 말 것`이라는 closed-book 문구를 받아 정상적으로 거절했습니다.

판정: **검색 후보는 성공했으나 최종 근거 선택이 실패한 B 유형**입니다.

### UAT-S11 — “진정은 어떻게 진행하는 거야?”

- 정리된 핵심 토큰은 대략 `진정`, `진행하는`, `거야`입니다. `진행`은 현재 절차 동작 어간 목록에 없고, `어떻게 진행하는 거야`도 절차형 정규식에 잡히지 않습니다.
- A8 본문 검색에서는 정답이 매우 높았습니다.
  - Vector: p.160 1위(0.66006), p.161 2위(0.63496), p.162 4위(0.63028)
  - BM25: p.161 1위(10.34163), p.160 2위(8.67638), p.162 5위(6.93727), p.163 7위(6.52147)
  - Hybrid: p.160 1위, p.161 2위, p.162 4위, p.163 9위
- 실제 Automatic에서는 p.75의 낙상예방 **image_description** 한 건만 최종 선택됐습니다. 이 설명에는 `진정 후`와 `진행하는 초기평가`가 함께 있어 질문 토큰 3개 중 2개가 일치했습니다.
- 당시 운영 로그에 남은 p.75 선택값은 Vector 순위 없음, BM25 2위, BM25 점수 9.32820, 내용 단어 일치율 0.6667, 결합점수 0.125였습니다. 2/3 경계를 충족해 살아남았습니다.
- 반면 정답 본문은 A8 Vector 점수가 약 0.63~0.66으로 0.70보다 낮았고, 운영 질문 토큰 형태 때문에 최종 선택을 통과하지 못했습니다.
- 추가 rag-memory 호출은 없었습니다. 따라서 추가 검색이 결과를 덮어쓴 것은 아닙니다.
- Gemini에는 p.75 한 건만 전달됐고, 답변도 그 근거가 낙상 예방이며 진정 절차는 없다고 정확히 구분했습니다.

판정: **정답 본문 선택 실패 + 관련 없는 이미지 설명 선택의 B 유형**입니다. p.75의 실제 운영 사전 필터 전체 순위는 결과 파일에 보존되지 않았지만, 위 최종 선택 점수와 source는 당시 로그·응답으로 확인됐습니다.

### UAT-S12 — “그중 진정 후에는 어떻게 관찰해?”

- `그중`은 앞 문맥을 가리키지만 검색 query는 현재 질문만 사용합니다. 검색 단계에서 앞 질문의 주제를 query에 보충하지 않습니다.
- 토큰에는 `그중`, `진정`, `후에`, `관찰`이 남아 실제 문서가 모든 표현을 만족하기 어렵습니다.
- A8에서는 p.161 2위, p.162 3위, p.163 9위로 찾았습니다. Vector 점수는 p.162 0.61847, p.161 0.60443으로 순위는 높지만 운영 독립 유지 기준보다 낮았습니다.
- 첫 Automatic 선택은 0개, 추가 검색도 0회였습니다. Gemini context에는 closed-book 문구만 들어갔습니다.

판정: **대화 의존 표현을 원 질문 단독 검색에 사용했고 후단 선택에서 모두 제거된 B 유형**입니다. Gemini 선택 실패나 Citation validator 문제는 아닙니다.

### UAT-T16 — “수혈간호를 전체적으로 핵심 요약해줘”

- A8 Vector 상위 10개는 모두 p.113~130 범위였고, Hybrid도 10개 중 9개가 기대 범위였습니다. 후보 수 부족이 아닙니다.
- 운영 토큰에는 `수혈간호`, `전체적`, `핵심`, `요약해줘`가 남습니다. 문서는 `수혈 간호`처럼 띄어 쓴 항목을 찾을 수 있어도 `전체적`, `핵심`까지 함께 담지 않습니다.
- A8 Vector 상위 점수도 0.61304~0.58433으로 0.70보다 낮았습니다. BM25 내용 일치율 2/3을 충족하지 못하면 순위가 좋아도 운영 후단에서 제거됩니다.
- 당시 Automatic 로그는 Vector 후보 20개, BM25 후보 10개를 만들었지만 최종 선택 0개였습니다.
- parent atomicity나 Gemini context 길이 때문에 잘린 것이 아닙니다. context를 구성하기 **전** 0개가 됐습니다.
- 절차 질문으로 감지되지 않아 최대 6개 확장도 적용되지 않았습니다. 다만 이 경우 핵심 원인은 상한보다 모든 후보가 제거된 것입니다.

판정: **넓은 질문의 coverage 표현을 내용 단어처럼 요구해 전부 제거한 B+G 유형**입니다.

### UAT-S06

`성인은 몇 분마다 모니터링해?`에는 현재 병원 질문 감지 목록의 `진정`, `간호`, `검사`, `치료` 같은 단어가 없습니다. `성인`, `분마다`, `모니터링해`만으로는 선행 rag-memory가 강제되지 않았고 Agent도 추가 검색을 부르지 않았습니다.

그런데 답변은 15분 간격 등 앞선 진정 답변과 일치합니다. 실제 평가 호출은 thread를 지정하지 않은 기본 대화에서 순서대로 실행됐고, Agent는 같은 workspace·사용자·기본 thread의 최근 20개 채팅을 불러옵니다(`server/utils/agents/index.js`의 `#chatHistory`). 따라서 이 답변은 현재 질문의 검색 근거가 아니라 앞선 대화 이력의 영향을 받았을 가능성이 매우 높습니다. 모델 자체 지식의 영향까지 저장 결과만으로 완전히 분리할 수는 없습니다.

### UAT-T15

`피 넣기 전에 뭐부터 체크해야 돼?`도 `수혈`, `혈액`, `간호` 같은 감지 단어가 없습니다. 검색 호출 없이 source 0개로 구체적인 수혈 답변이 생성됐습니다. 이 질문 직전에 여러 수혈 문항이 같은 기본 대화에 저장돼 있었으므로 S06과 같은 대화 이력 영향이 가장 유력합니다.

### Citation 단계 판정

- `memory.js`는 검색 source를 보관소에 넣습니다.
- `chat-history.js`는 그 보관소를 그대로 `response.sources`에 저장합니다.
- frontend는 sources가 0개이면 Citation을 렌더링하지 않습니다.
- S06·T15를 포함한 5건은 server 응답부터 0개였습니다. same-page dedupe, frontend relevance filter, streaming/history 렌더 차이가 원인이 아닙니다.

즉 S06·T15는 “검색 근거가 있었는데 Citation만 사라진 문제(E)”가 아니라, **현재 질문에서 검색이 실행되지 않아 source 생성 자체가 없었던 A+E 유형**입니다.

## 6. Citation 과다 문항

### 구조적 원인

1. `addRagMemorySources`는 첫 검색과 추가 rag-memory의 source를 모두 누적합니다.
2. 최종 저장 시 이 전체 배열을 `response.sources`로 저장합니다.
3. Gemini는 source별 사용 여부를 구조화해 반환하지 않습니다.
4. frontend는 질문·답변·excerpt의 단어와 3단어 연속 구문 겹침을 보고 추정합니다.
5. 자신 있게 좁히지 못하면 증거가 사라지는 것을 막기 위해 원본 sources 전체를 fallback으로 표시합니다.

| UAT-S09 | 1 | p.160, 161, 166, 162, 159 | 다섯 쪽 모두 | `성인·소아·진정`과 답변 문구가 폭넓게 겹침 |
| UAT-S14 | 0 | p.162, 324, 164, 14 | p.162, 164 | p.324·14는 제거되지만 회복 화면 p.164는 남음 |
| UAT-T03 | 0 | p.117, 130, 117, 127 | p.117, 130 | 같은 p.117은 1개로 합쳐짐 |
| UAT-T12 | 0 | p.124, 130, 121, 117 | 네 쪽 모두 | 답변이 네 근거의 준비 내용을 실제로 폭넓게 포함 |
| UAT-T13 | 0 | p.117, 130 | 두 쪽 모두 | 두 source 모두 관찰 답변과 문구가 겹침 |
| UAT-T17 | 2 | p.323, 128, 113, 332 | p.128 | frontend가 저관련 세 쪽을 제거함 |

따라서 과다 문제는 한 종류가 아닙니다.

- **서버 누적은 많지만 화면 필터가 정상적으로 줄이는 사례:** S03, T17
- **필터 0건 시 안전 fallback 때문에 모두 표시되는 사례:** S05
- **일반적인 단어·답변 구문이 많이 겹쳐 느슨하게 남는 사례:** S08, S09, S14
- **여러 페이지가 실제 답변을 함께 뒷받침할 가능성이 높은 사례:** T03, T12, T13. 이 세 문항은 단순히 “과다”라고 확정하기보다 간호사 검수가 필요합니다.

“답변에 실제로 사용된 source”는 현재 데이터로 확정할 수 없습니다. 문장별 citation ID가 없기 때문입니다. 위 표는 저장 source와 화면 표시를 확정하고, 실제 사용 여부는 문구 겹침으로만 추정한 것입니다.

## 8. 개선안 — 이번에는 적용하지 않음

### 1단계: 가장 안전한 개선

| 제안 | 범위 | A8 영향 | 검색 순위 영향 |
|---|---|---|---|
| 평가 21문항을 각각 독립 thread에서 실행 | 평가 도구만 | 없음 | 없음 |
| runtime에서 `원 질문 → 후보 → 후단 탈락 이유 → 최종 context source`를 ID·점수와 함께 로컬 진단 로그에 남김 | 관찰성 | 없음 | 없음 |
| 검색 미실행인데 source 없이 구체 답변한 경우를 검수 경고로 표시 | 평가/안전 검사 | 없음 | 없음 |
| Citation 저장/화면/실사용 추정을 구분해 검수표에 별도 열로 표시 | 문서/평가 | 없음 | 없음 |

우선 권장: **독립 thread 재평가와 진단 로그 보강**입니다. 이번 결과에는 같은 기본 대화 이력이 섞여 S06·T15의 답변 품질을 독립적으로 평가하기 어렵습니다.

### 2단계: 제한적 로직 개선 — 별도 승인 필요

| 제안 | 대상 | A8 영향 가능성 | 주의점 |
|---|---|---|---|
| 병원 질문 감지에 구어체·대화 문맥을 안전하게 반영 | S06, T15, S12 | 낮음~중간 | 검색 호출 여부가 바뀜 |
| 활용형 `진정할→진정`, `주의할→주의`처럼 임상 핵심어만 보수적으로 정규화 | S04 | 중간 | BM25 결과가 달라질 수 있음 |
| broad 요약 요청어를 coverage 내용 단어에서 제외하고 문서 주제어 중심으로 판단 | T16 | 중간 | source 선택이 달라짐 |
| image_description이 본문 근거 슬롯을 단독 점유하지 않도록 근거 종류를 구분 | S11 | 중간 | 최종 context 구성이 달라짐 |
| Citation 0건 fallback과 느슨한 일반 단어 매칭을 문항 유형별로 제한 | S05 등 | A8 없음 | 직원 화면만 달라질 수 있음 |

### 3단계: 검색 품질 영향 가능 — 현재 권장하지 않음

- Top-K 증가
- Hybrid 75:25 변경
- Vector 0.70 또는 BM25 2/3 기준 변경
- embedding/Chroma/후보 수 변경

이 단계는 A8 순위와 운영 검색 결과를 직접 바꿀 수 있습니다. 1·2단계 원인 재현 후 별도 승인 없이는 적용하지 않는 것이 안전합니다.

## 9. A8 기준선 보호

- Vector Hit@10: **100% (21/21)**, MRR **0.743**
- Hybrid Hit@10: **100% (21/21)**, MRR **0.738**
- 이번 분석에서 BM25, Vector, Hybrid 75:25, embedding, Top-K, source filter, query 처리, prompt, Automatic, rag-memory, Citation 코드를 수정하지 않았습니다.
- 개선안을 적용할 경우에는 A8뿐 아니라 **운영 후단을 통과한 최종 context source**도 별도 회귀 기준으로 확인해야 합니다.

## 10. 재현 방법

새 Gemini 호출 없이 다음 순서로 재현했습니다.

1. A8 JSON에서 문항별 Vector/BM25/Hybrid Top-10 순위와 점수를 확인했습니다.
2. 실제 Automatic 실행 JSON에서 답변, server source, event 유형, 추가 tool 호출 수를 확인했습니다.
3. `memory.js`와 `chat-history.js`로 context·source 저장 경로를 확인했습니다.
4. 저장 질문·답변·source에 현재 `citationFilter.js` 조건을 적용해 화면 필터 결과를 다시 계산했습니다.
5. 같은 PDF+page dedupe를 적용해 최종 Citation 수를 구분했습니다.

이 분석 과정에서 새 질문, 새 Gemini 답변, 새 embedding, Chroma 재색인을 실행하지 않았습니다.
