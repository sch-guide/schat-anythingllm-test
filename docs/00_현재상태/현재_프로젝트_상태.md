# SCHAT 기능 비교 테스트 현재 상태

## 이 저장소의 목적

기존 SCHAT을 교체하기 전에 문서 등록, 검색, AI 답변, 출처, 직원 로그인과 도구 기능을 별도 환경에서 확인하는 저장소입니다.

## 현재 확인된 상태

| 구분 | 현재 상태 |
|---|---|
| 저장소 | 기존 SCHAT과 분리된 별도 Git 저장소 |
| 화면 | SCHAT 병원용 이름과 기본 디자인 적용 |
| 화면 글꼴 | 일반 화면은 `Pretendard → Inter → system-ui → 운영체제 기본 글꼴` 순서의 전역 산세리프로 통일했습니다. 코드 블록과 고정폭 문자는 기존 monospace를 유지하며 외부 CDN이나 새 폰트 파일은 사용하지 않습니다. |
| 문서 화면 | 이 저장소 전용 `docs_view`로 분리 완료 |
| 폴더 정리 | 불필요한 배포·홍보 자료는 제거하고 웹 삽입 원본과 필수 자동검사 도구는 보존 |
| Explorer 순서 | 웹 문서, 현재 상태와 작업일지를 위로, 개발자용 파일을 맨 아래로 배치 |
| 검색 | Gemini Embedding 2 + ChromaDB 주 검색 + BM25 용어 보완 구현 |
| MiniLM | 새 SCHAT 검색 경로에서는 사용하지 않음 |
| 답변 생성 | 현재 직원 workspace는 Automatic 모드이며 AgentHandler가 Gemini 자유형 답변을 생성합니다. 답변 방식·prompt·길이·문체는 변경하지 않고, Agent가 실제 `rag-memory`로 찾은 병원 문서만 답변 출처로 보존합니다. |
| Docker | SCHAT 웹, ChromaDB, 내부 Python 안전검사 서비스 동시 실행 및 영구 저장 구성 완료. 안전검사 서비스는 연구용으로 보존하며 현재 테스트 웹 답변 경로에서는 호출하지 않음 |
| 기본 기능 확인 | 문서 등록, 임베딩, 색인, 검색, 답변과 출처 흐름을 별도 테스트 환경에서 확인 |
| 직원 로그인 | 직원 개인계정으로 부서·사번·이름·비밀번호를 입력해 로그인합니다. 사번이 고유값이고 내부 연결은 계정 id 기준입니다. 실패하면 이유와 관계없이 같은 문구가 보이고, 같은 IP나 사번으로 10분 안에 10번 실패하면 10분간 막힙니다. 새로 등록되었거나 관리자가 초기화한 직원은 로그인 화면의 `처음 사용하시나요? 비밀번호 만들기`에서 부서·사번·이름을 확인한 뒤 비밀번호를 직접 만듭니다. 관리자는 비밀번호를 만들거나 전달하지 않습니다. 사번이 없는 기존 계정은 기존 계정 링크로 들어오고 기존 비밀번호를 그대로 씁니다. 실제 아이디와 비밀번호는 문서에 기록하지 않습니다. |
| 임상 안전검사 | `SCHAT_SAFETY_GATE_ENABLED=false`가 현재 테스트 웹 기본값입니다. Python `/prepare`·`/validate`와 PASS/FAIL·원문 대체는 직원 실제 답변 경로에서 호출하지 않으며, 코드와 기존 검사는 연구용으로 보존합니다. |
| 답변 표시 방식 | Automatic 모드에서는 AgentHandler의 자유형 답변을 기존 Markdown 화면에 그대로 표시합니다. Query 모드의 structured response와 허용 출처 ID 검증 코드는 보존하지만 현재 Automatic 답변에 이식하지 않습니다. |
| 절차 답변 표시 | Automatic 답변은 AgentHandler가 만든 자유형 Markdown을 그대로 표시합니다. 기존 Query 답변·과거 대화의 절차 presentation renderer는 삭제하지 않고 호환용으로 유지합니다. |
| 절차 출처 badge | 내부 SourceUnit ID는 브라우저로 보내지 않고 공개용 `sourceIndexes`만 전달합니다. 문장마다 번호를 반복하지 않고 절차 답변 맨 아래에 사용 출처를 중복 없이 한 번만 표시하며, badge는 기존 출처 sidebar를 엽니다. 기존 하단 출처 표시도 유지합니다. |
| 출처 표시 | 직원에게 문서명·페이지·항목명을 표시하고, 검증된 근거 원문이 있으면 출처 상세에서 함께 보여줍니다. 내부 SourceUnit ID·경로·metadata·SVG는 공개하지 않으며 과거 대화처럼 원문이 없으면 기존 정보만 표시합니다. |
| 출처 원문 펼치기 | Automatic Agent가 실제 `rag-memory`로 검색한 출처만 답변 아래에 누적·중복 제거해 Citation 행으로 표시합니다. 중복되던 별도 출처 버튼과 아이콘 묶음은 제거했습니다. 각 행의 `근거 원문 보기`를 누르면 여백과 문단 간격을 확보한 원문 뒤에 직접 연결된 이미지만 표시하며, 이미지가 없으면 빈 영역을 만들지 않습니다. |
| PDF 원본 페이지 보기 | 앞으로 관리자 화면에서 새 PDF를 등록하면 검색용 처리와 함께 원본을 영구 보관합니다. Citation의 `근거 원문 보기`는 원본이 연결된 경우 브라우저 PDF viewer로 실제 출처 페이지를 먼저 표시하고, 원본이 없거나 열리지 않으면 기존 excerpt와 직접 연결 이미지를 보여줍니다. 휴대폰(폭 767px 이하)에서는 원문 전용 전체 화면이 열리고 `← 채팅으로`, 문서명·쪽, `PDF 원문`·`텍스트 원문` 전환을 제공합니다. 출처 쪽을 화면 폭에 맞춰 그리며 확대·축소가 되고, 뒤로가기로 같은 대화 위치에 돌아갑니다. PC 화면은 바뀌지 않았습니다. 직원 화면에는 내부 문서 ID와 저장 경로 대신 추측하기 어려운 `pdfRef`만 전달합니다. |
| 기존 PDF 원본 연결 | 관리자 문서 목록의 원본 PDF 행에서 `원본 PDF 연결`을 눌러 기존 검색 자료에 원본만 연결할 수 있습니다. 기존 page JSON, ChromaDB 본문 벡터, BM25, 이미지 설명은 다시 만들지 않습니다. 현재 workspace 연결 대상은 `2026실무지침서 (26.7).pdf` 461쪽과 `검사 및 시술(26.04.07).pdf` 82쪽입니다. |
| Renal biopsy 체크리스트 MVP | `검사 및 시술(26.04.07).pdf` p.56의 원문 구조를 규칙 기반으로 읽어 파일형 체크리스트로 자동 저장합니다. 검사목적은 설명형으로, 실제 확인 항목만 체크박스로 표시합니다. 직원은 관련 질문의 답변 아래 버튼에서 사용할 수 있고, 관리자는 문서 화면에서 보기·수정·원본 p.56 보기가 가능합니다. 승인이나 재색인은 필요하지 않습니다. |
| 검사·시술 체크리스트 | `검사 및 시술(26.04.07).pdf`의 표준 양식 페이지를 원본 PDF 글자 좌표로 읽어 체크리스트를 자동 저장합니다. 현재 직원에게 보이는 체크리스트 55개(Renal biopsy 포함)와 관리자 검토 필요 25개입니다. 모든 제목·항목·세부 문장은 해당 페이지 원문과 대조해 통과한 것만 표시하고, 칸 안에 하위 표가 있는 페이지는 검토 필요로 숨깁니다. 2026-09-28: 체크리스트가 없던 16쪽(CT, MRI, EBUS, PEG 등)은 원문 줄을 그대로 옮긴 초안을 **검토 필요** 상태로 저장했습니다(직원에게 숨김, 간호사 검토 대기). 2026-09-29: `SCHAT 관리자 설정 > 체크리스트 관리`에서 상태(검토 필요/공개/숨김)를 바꾸고, 원본 PDF 쪽을 열어 대조하고, 내용과 찾는 이름을 직접 고칠 수 있습니다. 직원에게는 공개만 보이며, 관리자가 정한 상태·수정은 자동 추출이 덮어쓰지 않습니다. 2026-09-29: 관리자가 세부 줄마다 체크박스를 켜고 끄고 직원 화면 미리보기로 확인할 수 있습니다(설정 없는 기존 체크리스트는 예전 모양 유지). 문서를 올려 자동으로 만들어진 체크리스트는 항상 검토 필요로 들어갑니다. |
| 관리자 문서 목록 | 안정적인 원본 식별자가 있는 PDF는 페이지 단위 저장 행을 숨기고 원본 PDF당 한 행만 표시합니다. 현재 등록 자료는 원본 PDF 2개로 표시되며, PDF 전체 선택은 기존 자식 문서 선택과 bulk 제거 API에 연결됩니다. 원본 단위 API가 없는 pin·watch는 부모 행에 표시하지 않습니다. |
| 데이터 커넥터 | SCHAT에서 사용하지 않는 GitHub·GitLab·Gitea·YouTube 자막·웹사이트 대량 수집·Confluence·Drupal Wiki·Obsidian·Paperless-ngx의 관리 탭, 공개 API와 collector 구현을 제거했습니다. PDF 직접 업로드와 일반 link 재동기화는 유지합니다. 단일 URL 직접 등록(웹사이트 가져오기)은 2026-09-27부터 업로드 화면에서 숨겼고 서버 기능은 보존합니다. |
| 프로젝트 설명 화면 | `docs_view/index.html`을 비개발자용 프로젝트 설명 화면으로 개편했습니다. 실제 Compose·코드·공식 문서를 정적으로 읽어 모델, Embedding, ChromaDB, BM25, Docker 서비스, 폴더, 검사와 변경 이력을 공개용 JSON과 HTML에 자동 반영하며 인수인계 내용도 화면에서 확인할 수 있습니다. `.env`, API 키, PDF와 병원 문서 본문은 읽거나 공개하지 않습니다. |
| 인수인계 문서 | `03_전체_공식문서` 밖의 별도 `05_인수인계` 폴더에 배치하고, 설명 HTML 자동 생성기도 새 위치를 사용합니다. |
| 실제 질문 검수 | 합성 비민감 질문 1건 실행. 구조화 형식은 정상 처리됐으나 필수 근거 누락으로 AI 후보를 차단하고 원문 기반 답변으로 대체 |
| 검색 정밀도 | 질문의 핵심어·항목명·의미 점수를 함께 확인하고 약한 근거로 결과 수를 채우지 않도록 구현했으며, 승인 문서 재색인까지 완료 |
| 근거 부족 처리 | 정확 용어가 없고 의미 점수도 낮으면 `등록된 병원 지침에서 관련 근거를 확인할 수 없습니다.`로 중단하도록 검증 완료 |
| 안전 대체 답변 | Gate OFF 직원 경로에서는 임상 validator 실패에 따른 원문 대체 답변을 사용하지 않습니다. 근거 0건, Gemini 실패, structured parsing 실패만 안전 문구로 중단합니다. |
| 항목명 | 원본 항목명을 우선 보존하고, 번호·마크다운·독립된 짧은 제목처럼 문서에 명시된 제목만 새 색인에 저장하도록 준비 |
| 문서 등록 배치 | 업로드 API가 실제 처리한 상대 `docpath`만 공개하고 화면은 그 정확한 batch만 선택합니다. 목록 첫 100건이나 폴더 전체를 다시 읽어 큰 PDF 일부만 등록되던 경로를 제거했으며, 조회 실패는 성공처럼 넘기지 않습니다. |
| 안전한 색인 복구 | 복구 도구는 기본 dry-run이며, 정확히 확인된 시작·완료 상태만 처리합니다. SQLite 백업과 staging Chroma 검증을 먼저 거치고 실패 시 원상복구하며, 교체 전 collection도 롤백용으로 보존합니다. |
| 현재 색인 | workspace 내부 본문 문서 543건을 유지하고, live Chroma에는 본문 벡터 654개와 이미지 설명 보조 벡터 945개가 있습니다. 이미지 벡터 945개는 고유 이미지 설명 916개와 작업 전부터 있던 중복 29개로 구성됩니다. 교체 전 151개 collection과 SQLite 백업은 롤백용이라 live 합계에 포함하지 않습니다. |
| 이미지 설명 전체 보충 | 고유 이미지 1,172개를 확인했고 기존 설명 34개를 재사용했습니다. 누락 1,138개를 재시도 없이 23개 배치로 처리해 882개 설명 생성에 성공했고 256개는 Google API 사전 결제 크레딧 소진으로 실패 상태를 기록했습니다. 따라서 현재 설명 보유 이미지는 916개이며, 성공·실패 hash 모두 재실행 시 다시 Vision 호출하지 않습니다. |
| 이미지 보조 벡터 반영 | cache에 성공 저장된 신규 설명 882개만 Gemini Embedding으로 변환해 221개 batch 요청으로 Chroma에 반영했습니다. Vision은 다시 호출하지 않았습니다. live `image_description` 벡터는 63개에서 945개로 늘었고 고유 설명 916개가 모두 검색 후보가 됐습니다. 본문 벡터는 작업 전후 654개이며 snapshot hash도 동일합니다. |
| 페이지·항목명 | 대상 실무지침서의 페이지 문서 461개와 다른 문서 82개를 보존했습니다. 필수 확인 페이지가 모두 존재하고 대상 페이지 중복 0건·누락 0건임을 확인했습니다. |
| 재시작 검증 | Docker 재시작 뒤에도 ChromaDB 데이터, 계정과 기존 대화가 유지됐고 세 서비스가 모두 healthy입니다. |

## 현재 주의사항

- 실무지침서 461개 페이지 단위의 색인 복구는 완료했지만, 다양한 실제 질문의 최종 문장 품질을 사람이 검수하는 일은 계속 필요합니다.
- 지정한 7개 질문은 로컬 근거 선택까지만 확인했습니다. 실제 Gemini 답변을 검수하려면 전송할 질문과 선택 근거, 전송 대상에 대한 구체적인 승인이 별도로 필요합니다.
- 현재 테스트 웹은 Python 임상 의미 validator를 거치지 않습니다. 직원 workspace는 Automatic 모드이며 AgentHandler의 기존 자유형 답변과 `rag-memory` 검색을 사용합니다. Query 모드의 closed-book structured JSON과 허용 출처 ID 검사는 코드로 보존하지만 현재 Automatic 답변에는 적용하지 않습니다.
- 교체 전 151개 collection과 SQLite 백업은 복구용입니다. 상태를 확인하기 전에 재업로드하거나 Chroma volume을 삭제하지 않습니다.
- 기존 합성 문서는 등록 당시 한글 문서명이 이미 손실되어 원래 이름을 복구할 수 없습니다. 화면에서는 깨진 문자를 제거한 `SCHAT_.txt`를 표시하고, 없는 페이지·항목은 생략합니다.
- API 키, 환자정보와 병원 원문은 문서 화면에 저장하지 않습니다.
- 기존 두 PDF는 검색 자료만 등록된 상태이므로 관리자가 문서 목록의 `원본 PDF 연결`에서 원본을 한 번 선택해야 실제 PDF 페이지 보기가 활성화됩니다. VS Code 폴더에 직접 파일을 넣거나 재색인할 필요는 없습니다.
- 이번 결과는 기능 비교 테스트이며 정식 Production 승인으로 간주하지 않습니다.

## 이미지 질문 기능

- 직원 채팅에서 JPG·JPEG·PNG·WebP 이미지 1장(최대 5MB)을 질문과 함께 첨부할 수 있습니다.
- 이미지는 상황 이해용으로만 사용하고, 질문 글로 SCHAT 등록 문서를 검색합니다.
- 최종 답변은 등록 문서 근거로 만든 structured JSON과 허용 출처 ID를 확인한 뒤 표시합니다.
- 현재 기본값에서는 Python 안전검사와 원문 기반 대체 답변을 사용하지 않습니다. 필요하면 연구 목적으로 Gate를 다시 켤 수 있습니다.
- 이미지 원문은 일반 로그와 안전 채팅 기록에 저장하지 않습니다.
- 가짜 이미지와 가짜 Gemini 응답 자동검사는 완료했지만 실제 Gemini 이미지 호출은 아직 실행하지 않았습니다.

## PDF 내부 이미지 활용

- 새로 등록하거나 다시 색인하는 PDF에서는 페이지 안의 의미 있는 이미지를 문서별 저장 폴더에 분리해 보관합니다. 기존 PDF 본문 추출과 본문 벡터는 그대로 유지합니다.
- 이미지마다 파일 내용의 SHA-256 해시를 사용해 중복 설명 요청을 막고, Gemini 설명이 실패해도 PDF 수집은 계속 진행합니다.
- 이미지 설명은 기존 본문과 섞지 않고 `image_description` 보조 벡터로 저장합니다. Gemini에 전달하는 본문 근거에는 이미지 설명 결과를 최대 1개만 허용해 기존 본문 검색을 우선합니다.
- 관련 이미지 후보는 본문 근거 top-N과 별도로 보존합니다. 따라서 이미지 설명이 Gemini 본문 근거 슬롯에 들지 않아도 질문 초점 검사를 통과하면 `relatedImages` 경로로 전달됩니다. Gemini가 직접 사용한 이미지를 먼저 포함하고 동일 hash를 제거한 뒤 직원 화면에는 최대 3개만 표시하며, 내부 저장 경로와 문서·벡터 ID는 공개하지 않습니다.
- 본문 검색어가 확장되더라도 관련 이미지 검색에는 직원이 실제 입력한 원문 질문을 별도로 사용합니다. 이미지용 벡터·BM25 후보와 질문 초점 필터만 원문 질문으로 계산하므로, 본문 top-N과 Gemini 답변 근거·출처 순위는 이전과 같습니다.
- 이미지가 없거나 이미지 metadata가 없는 기존 문서는 이전 방식으로 정상 작동합니다. 기존 문서에 이 기능을 적용하려면 재업로드 또는 재색인이 필요합니다.
- mock으로 설명 생성·실패 처리·검색 제한·화면 연결을 검증한 뒤, 사용자 승인 범위의 누락 이미지 14장만 Gemini Vision으로 1회씩 설명했습니다. 재시도와 PDF 전체 전송은 하지 않았습니다.
- 2026-09-28: 사진·그림·이미지·도식·도표·그래프를 요청하는 질문에서만, 질문 주제 단어를 모두 가진 최상위 의미 검색 조각을 통과시키고, 근거 쪽의 사진(가장 구체적인 주제 단어 포함)과 근거에서 2쪽 이내의 사진(주제 단어 모두 포함)을 출처에 붙입니다. 일반 질문의 검색·출처는 그대로입니다.
- 관련 이미지는 같은 페이지에 있다는 이유만으로 표시하지 않습니다. 검증된 `image_description` 검색 결과만 사용하고 `related_image_keys` 전체를 펼치지 않아 로고·장식·관련 없는 표가 따라오는 문제를 막습니다.
- 수정 전 저장된 과거 답변의 페이지 일괄 이미지에는 직접 관련성 표식이 없으므로 다시 열어도 표시하지 않습니다.
- 새 PDF 업로드는 이미지 SHA-256 cache를 먼저 확인하고 새 hash만 설명합니다. 기본 배치 크기는 50개, 실행당 상한은 1,150개이며 성공·빈 응답·실패 상태를 즉시 저장합니다. 같은 이미지가 다른 페이지로 이동하거나 문서를 다시 올려도 기존 설명을 재사용하고, 이미지 내용이 바뀌어 hash가 달라진 경우에만 새 설명 대상이 됩니다.
- 전체 보충 dry-run은 고유 이미지 1,172개, 신규 Vision 대상 1,138개로 승인 상한과 정확히 일치했습니다. 실제 Vision 실행은 1,138회, 23개 배치였고 성공 882개·실패 256개·빈 응답 0개였습니다. 결제 복구 뒤에는 Vision을 재호출하지 않고 cache의 성공 설명 916개만 사용했습니다. 기존 고유 벡터 34개를 제외한 882개를 221개 Gemini Embedding batch 요청으로 추가했고, 최종 live `image_description` 벡터는 945개입니다. 기존 중복 29개는 보존했지만 새 중복은 만들지 않았습니다.
- Embedding 전용 backfill은 각 batch의 Chroma upsert 직후 진행상태를 저장합니다. 중간 실패 후 다시 실행하면 실제 Chroma에 이미 있는 안정적 `문서 + image_key` 벡터를 제외하므로 성공한 벡터를 다시 생성하지 않습니다.
- `NRS 통증척도는 어떻게 평가해?`처럼 자연스러운 질문 표현은 핵심 동사 형태로 정규화해 관련 p.100 근거가 검색 안전 기준에서 탈락하지 않게 했습니다. 질문의 핵심 척도가 이미지 설명에 실제로 포함되면 NRS·FPRS·FLACC가 함께 보이는 혼합 통증평가 화면도 허용하고, 질문 척도는 없고 경쟁 척도만 있는 이미지는 계속 제외합니다. 검색 기준 전체를 낮추거나 특정 NRS 답변을 하드코딩하지 않았습니다.

- 직원 질문에 검사·시술 이름이 있으면 해당 체크리스트 버튼이 나옵니다. 영문 약어는 단어 단위로만, 한글 이름은 단어 시작에서만 인정하고 더 긴 이름을 우선합니다(예: `위내시경점막하박리술` 질문에 `위내시경` 체크리스트가 함께 뜨지 않음). 여러 체크리스트를 동시에 띄울 수 있고, 위치·크기·체크·접힘 상태는 체크리스트별로 따로 유지됩니다. 2026-09-28부터 흔히 부르는 이름(예: 폐생검→PTNB, 간생검, 홀터, 심장 CT)과 쉼표로 묶인 이름도 인식합니다(`commonNames.js`, 찾기 전용). 헷갈리는 이름(EMR, LP, pacemaker, ESD 등)은 넣지 않았습니다.
- 직원용 체크리스트는 상위 항목과 세부 줄마다 체크박스를 표시합니다. 상위 체크는 세부 줄 전체 선택·해제, 일부만 체크하면 상위는 중간 상태(-)로 표시되고, 체크한 세부 줄은 취소선과 흐린 글자로 바뀝니다. `검사목적`과 `검사장소/이동수단`은 읽기용 정보로 체크박스 없이 표시합니다. 저장된 체크리스트 JSON과 관리자 모달은 바꾸지 않았습니다.
- Renal biopsy Citation은 내부에 저장된 검색 source 4개를 변경하지 않고 직원 화면에서만 직접 근거를 선별합니다. 실제 저장 답변 검증에서는 p.56만 표시되고 일반 검색 후보인 p.8·p.14·p.30은 숨겨졌습니다. 직접 근거를 확실히 판단하지 못하면 저장된 전체 Citation을 보여주는 안전 fallback을 사용합니다.

- 좌측 사이드바는 별도 브랜드 배지 없이 `SCHAT` 이름만 표시합니다(기존 `SCHC` 배지 제거). 데스크톱과 모바일 사이드바가 같은 브랜딩을 사용합니다.
- 로그인 화면은 제공받은 파란색 `SCH` 로고 한 파일(`frontend/src/media/logo/sch-logo.png`, 원본 188×68px)을 왼쪽 병원명 옆(높이 28px)과 오른쪽 `병원 실무지침 AI` 옆(높이 32px, 모바일은 둘 다 22px)에 사용합니다. 더 큰 원본이 없어 화면 밀도 3배까지 확대 없이 표시되는 크기로 맞췄습니다. 원본 이미지 좌우 가장자리의 밝은 선(왼쪽 1px, 오른쪽 2px)은 파일을 바꾸지 않고 화면 표시에서만 가리며, 로고와 옆 글자 간격은 9~10px(모바일 8~9px)입니다. 기존 초록색 십자 로고, 작은 `SCH` 글자, `웰컴!` 문구는 제거했고 `SCHAT에 로그인하세요.`는 유지합니다. 모바일 로그인 화면의 가로 넘침도 함께 고쳤습니다.
- 브라우저 탭 아이콘(`favicon.png`, `favicon.ico`)은 AnythingLLM 기본 아이콘 대신 같은 SCH 로고를 탭 크기에 맞게 정사각형으로 자른 이미지(128px 원본 픽셀 그대로, 16·32·48px는 단계적으로 축소)를 사용합니다. 서버가 `/favicon.png` 경로를 고정해 쓰므로 파일만 교체했습니다.
- 답변을 기다리는 동안에는 내부 Agent·tool 이름과 실행 JSON을 표시하지 않고 `답변 생성 중 · N초`만 1초 간격으로 표시합니다. 실제 답변 문장이 시작되거나 실행이 끝나면 이 표시는 사라집니다.
- 직원용 Citation은 검색 결과를 바꾸지 않고 화면에서만 같은 PDF의 같은 페이지를 하나로 합칩니다. 행에는 `출처 N · 파일명 · p.N`만 표시하며, 서로 다른 페이지와 서로 다른 PDF는 각각 유지합니다.
- 실제 Docker 브라우저 재검증에서 최신 frontend가 반영되지 않았던 컨테이너를 재빌드했고, 같은 UUID를 쓰는 Agent 상태 문구가 첫 답변 조각 앞에 합쳐지던 WebSocket 표시 결함도 수정했습니다. 로컬 이벤트 재생 기준으로 대기 중에는 타이머만 보이고, 답변 시작·완료 뒤 내부 상태 문구가 남지 않습니다.
- 저장된 실제 출처 4개(p.113 두 개, p.116 한 개, p.114 한 개)는 직원 화면에서 Citation 3개로 표시됩니다. p.113은 한 행이며 항목명은 숨겨지고, `근거 원문 보기`의 PDF viewer는 실제 113페이지를 열며 인증 PDF 요청은 HTTP 200입니다.
- 채팅 설정 메뉴에는 글자 크기와 다크모드만 표시합니다. 추억, 채팅 내보내기와 채팅 링크 복사는 SCHAT 화면에서 숨겼습니다.
- 직원 채팅 입력창은 글자 입력과 전송 버튼만 있습니다. 이미지 첨부·안내문, `+ 도구`, `/` 도구 메뉴, 마이크, 채팅창 파일 끌어놓기는 화면에서 껐습니다(서버 코드는 보존). 새 대화는 `+ 새 대화` 버튼 하나이며, 첫 질문 전의 빈 대화는 목록에 보이지 않습니다.
- 오른쪽 위 사용자 버튼은 사람 아이콘이며 `로그아웃`만 제공합니다. 빈 화면의 바로가기(에이전트 생성·워크스페이스 편집·문서 업로드)와 문서 업로드 창의 웹사이트 가져오기는 숨겼습니다.
- 다크모드는 기존 테마 기능을 그대로 사용하므로 선택 상태가 브라우저에 저장됩니다. 병원 색 적용 때 다크모드에도 밝은 색 값이 들어가 사이드바가 밝게 보이던 문제를 고쳐, 블랙·차콜 바탕에 딥 네이비 선택 표시와 은은한 파란 테두리로 사이드바·검색창·새 대화 버튼·입력창·오른쪽 위 메뉴·관리자 화면을 맞췄습니다.
- 비개발자용 화면 디자인 안내는 `03_전체_공식문서` 밖의 별도 `04_화면디자인` 폴더에 모았습니다. 실제 SCHAT 로고, 다크모드 버튼과 화면 검사는 앱이 안정적으로 실행되도록 `frontend`의 원래 컴포넌트 위치에 두었습니다.
- 채팅 우측 상단의 모델 선택 표시는 숨겼지만 모델 선택 컴포넌트와 실제 Gemini 설정은 삭제하지 않았습니다.
- 답변 아래 모델명·응답 시간·초당 토큰 표시는 숨겼지만 내부 측정 코드와 데이터는 보존합니다.
- 사이드바 하단 렌치(SCHAT 관리자 설정)는 로그인 모드의 관리자 또는 단일 사용자 모드에서만 표시합니다. 일반 직원 계정에는 표시하지 않습니다.
- 사용자 역할은 관리자 화면에서 `관리자`와 `직원` 두 가지만 고를 수 있습니다. 서버의 매니저 역할은 지우지 않았으며, 현재 매니저 계정은 없습니다. 예전 매니저 계정이 있으면 `매니저(이전 역할)`로 그대로 보이고 관리자 또는 직원으로 바꿀 수 있습니다.
- 검색, Gemini, Embedding, ChromaDB, BM25, 출처와 관련 이미지 처리 코드는 이번 화면 변경에서 수정하지 않았습니다.

## Automatic 답변과 실제 검색 출처

- 직원 workspace는 Automatic 모드이며 기존 AgentHandler의 Gemini 자유형 답변 방식을 그대로 사용합니다. Query용 검색 확장이나 structured JSON을 Automatic 경로에 넣지 않았습니다.
- 병원 문서 관련 질문은 첫 Gemini 자유형 답변을 만들기 전에 기존 `rag-memory` handler를 사용자 원문 질문으로 정확히 1회 실행합니다. 기존 검색 토큰·질문 의도 판별을 재사용하고 임상 약어는 일반 형식으로 판별하며, 날씨 같은 일반 질문은 강제 검색하지 않습니다. 이후 추가 검색은 기존 Agent 판단에 맡깁니다.
- `rag-memory`가 실제로 반환한 source 자체의 text를 원문으로 사용합니다. 별도 `contextTexts` 배열의 같은 순번을 추정해 연결하지 않으므로 다른 문서의 원문이 잘못 붙는 일을 막습니다.
- Agent가 한 답변에서 `rag-memory`를 여러 번 호출하면 실제 검색 출처를 계속 모으고, 내부의 안정적인 문서 식별값으로 중복만 제거합니다. 이 내부 식별값은 브라우저에 공개하지 않습니다.
- 공개 출처에는 문서명·페이지·항목명·정제된 실제 원문만 포함합니다. 내부 ID, vector ID, metadata 전체와 저장 경로는 제외합니다.
- 출처별 이미지는 실제 검색 source의 단일 `image_key` 또는 직접 검색된 `image_description`의 단일 `image_key`만 사용합니다. 최종 공개 직전에도 사용자 원문 질문으로 초점을 다시 확인하고, 같은 페이지의 전체 이미지 목록은 사용하지 않습니다. 로고·장식 이미지와 질문 척도가 없는 경쟁 척도 전용 이미지는 제외하며 출처별 최대 3개로 제한합니다. 혼합 척도 이미지는 질문 척도가 설명에 포함된 경우에만 허용합니다.
- 기존 Query 답변의 하단 관련 이미지 기능은 그대로 보존합니다.
- 실제 Automatic 경로로 `NRS`, `NRS 통증척도는 어떻게 평가해?`, `FPRS`, `통증 점수 설명`, `수혈 절차 알려줘`를 확인했습니다. 다섯 답변 모두 실제 검색 원문 출처가 저장됐고 중복·내부 정보 노출이 없었습니다. 직접 이미지 근거가 검색된 `통증 점수 설명`에는 이미지 1개가 연결됐으며 NRS 출처에 FPRS 이미지와 로고·장식 이미지는 연결되지 않았습니다.
- 서버 회귀 21개와 화면 회귀 11개, production build가 통과했고 `schat-web`, `schat-chromadb`, `schat-safety-evaluator`가 모두 healthy임을 확인했습니다.
- 선행 검색 결과는 가짜 function/tool-result 메시지로 만들지 않고 마지막 사용자 메시지의 병원 문서 context에 넣습니다. 검색 결과가 없으면 등록 문서에서 근거를 찾지 못했으며 일반 지식으로 보완하지 말라는 closed-book 문구만 전달합니다.
- 승인 후 실제 Automatic 요청 5건을 재시도 없이 실행해 400 오류가 사라지고, 앞의 병원 질문 4건은 첫 `rag-memory` 호출에 원문 질문을 사용하며 날씨 질문은 강제 검색하지 않음을 확인했습니다. 다만 검증용 계측 래퍼가 `rag-memory`의 실행 문맥을 보존하지 못해 이 5건의 출처·원문·이미지 결과는 유효한 제품 판정 자료로 사용할 수 없습니다. 추가 Gemini 호출 없이 서버·화면 회귀검사와 production build만 확인했으며, 실제 화면의 출처 결과는 다음 승인된 1회 검수에서 다시 확인해야 합니다.
- 최신 실제 브라우저 `NRS` 1회 검수에서 Automatic 답변과 출처 4개는 저장됐지만 출처별 이미지는 0개였습니다. 이미지 요청 API 자체는 HTTP 200을 반환했으나, `relatedImageSources`가 `memory.js`에 전달될 때 질문 초점 검사에 필요한 이미지 설명 `text`가 없어 안전하게 연결할 수 없는 것을 확인했습니다. 요청 범위 밖의 검색 반환 코드는 수정하지 않았습니다.
