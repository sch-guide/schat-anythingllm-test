### 1-1. 모든 작업에 공통으로 반복된 절차

거의 모든 작업이 같은 순서로 진행됐다. 팀원이 그대로 따라 할 수 있는 패턴이다.

1. 코드 먼저 조사(현재 구조, 재사용할 기능 찾기)
2. 필요하면 설계 문서(`docs/superpowers/specs/`)나 계획 체크리스트(`docs/superpowers/plans/`) 작성
3. 구현 → 단위 테스트(frontend `node --test`, server는 컨테이너 안에서 실행)
4. Docker 재빌드: `docker compose up -d --build --force-recreate --no-deps schat-web`
5. **실제 브라우저 검증**: 컨테이너 안 Puppeteer(Chromium) 또는 PC의 실제 Chrome을 CDP(Chrome 원격 제어 방식)로 조작. 테스트 계정과 가상 데이터만 사용하고, 끝나면 테스트 데이터와 대화방을 삭제
6. 문서 갱신: `docs/00_현재상태/현재_프로젝트_상태.md`, `docs/01_작업일지/날짜_주제.md` + README 목차, `python 문서도구/문서화면_만들기.py`로 docs_view 재생성, `python 검사/문서화면_분리_검사.py`
7. `git diff --check`(공백 오류 검사)
8. 사용자가 정한 보고 형식으로 완료 보고. commit·push는 사용자가 요청할 때만

### 문제 1 — Codex가 "완료"라고 적었지만 실제로는 덜 끝난 작업

- **당시 하려던 것:** Codex가 크레딧 소진으로 멈춘 체크리스트 작업창·Citation 거르기 작업 이어받기

### 문제 21 — 재검색 횟수 제한 설정(AGENT_MAX_TOOL_CALLS)이 실제로는 지켜지지 않음

- **당시 하려던 것:** 느린 재검색을 줄이는 두 방식 비교
  - 방식 A: 미리 검색했으면 첫 차례에 도구를 빼기(`SCHAT_AGENT_SKIP_TOOLS_AFTER_FORCED_SEARCH`, 새로 만듦, 기본 꺼짐)
  - 방식 B: `AGENT_MAX_TOOL_CALLS=2`(원래 있던 설정, 기본 10)
- **발생한 현상:**
  - 방식 A는 빠르지만 답을 잃음("수혈 종류", "항생제 피부반응검사"에서 "확인되지 않습니다")
  - **방식 B는 한도가 지켜지지 않음:** 한도에 걸린 뒤 도구 목록을 빈 채(`functions=[]`)로 보내도 Gemini가 계속 검색 요청을 보냈고, 코드가 그것을 실행함. "항생제 피부반응검사"에서 9번까지 감(입력 약 31만 토큰)
- **다음 시도(방식 C, `SCHAT_AGENT_RESEARCH_MODE=bounded`):** 미리 검색한 근거가 충분하면 도구 없이 답, 부족하면 추가 검색 최대 2회, 초과 요청은 **코드에서 실행하지 않음**
  - 1차: "충분" = 서로 다른 조각 3개 이상 + 2쪽 이상. 초과 시 근거만으로 답하라고 다시 요청하고, 그래도 검색만 요청하면 "확인되지 않습니다"

### 문제 31 — "관리자용 검색 점수 디버그 표시"를 어디에 넣을지 모호한 요청

- **AI 질문 선택지:** SCHAT 관리자 화면(추천) / docs_view에 설명만 추가 / 지금은 하지 않음 → 사용자 선택 "docs_view에 설명만 추가"
- **해결:** `05_인수인계/검색_점수_읽는_법.md` 추가(점수 뜻, fusionScore = `0.75 ÷ vectorRank + 0.25 ÷ bm25Rank`, 계산 예시, 합산 뒤 거르기 설명)
- **현재 상태:** 해결 완료(실제 관리자 화면 표시 기능은 미구현, 버전 4 후보)

## 6. 다른 프로젝트·다른 AI·팀원 코드에서 가져온 부분

> 이 대화에서 확인되는 범위만 적는다. 이 대화 이전의 이식 과정은 대부분 `[확인 불가]`다.

### 6-1. AnythingLLM (오픈소스, 서비스 기반)

- **원래 우리 방식:** SCHAT 원래 버전은 Python으로 만든 검색기와 평가 도구. 상위 폴더 `sch-guide-ai`에 있음 `[다른 대화에서 이어진 것으로 추정]`
- **비교한 방식:** AnythingLLM(React/Vite 화면 + Express/Prisma/SQLite 서버, 로그인·권한·문서관리·에이전트 기능 내장)
- **가져온 부분:** 로그인·세션(JWT), 비밀번호 bcrypt, 사용자·작업 공간·대화 저장 구조(`workspace_chats`), 문서 업로드·collector(PDF 추출), Automatic(에이전트) 경로(AgentHandler → aibitat → rag-memory 도구), 관리자 설정 화면 틀
- **우리 프로젝트에 맞게 바꾼 부분(이 대화에서 확인):** 관리자 메뉴를 "SCHAT 관리자 설정" 하나로 통합하고 나머지 메뉴 숨김(코드는 지우지 않음), 영어 용어 한글화, 사번 로그인 추가, 매니저 역할 화면에서 제거, 업로드에서 웹사이트 가져오기 숨김, Default System Prompt 상속 수정
- **가져온 뒤 발생한 문제:** 관리자 설정 fallback이 영어 기본 문장이었음(문제 8), compose가 키를 덮어씀(문제 9), 신고·알림 외래키가 계정 삭제를 막음(문제 15), 라이트 테마 `.text-white` 전역 재정의, 에이전트의 도구 호출 한도가 강제되지 않음(문제 21)
- **최종 구조:** "AnythingLLM의 서비스 기반 + SCHAT이 직접 만든 병원 문서 검색·병원 전용 기능"(CLAUDE.md 표현)

## 9. AI 질문법에서 배울 점

### 9-1. 효과적이었던 질문

**① 변경 금지 목록 + 실제 브라우저 검증 + 보고 형식이 있는 명세서**
- 실제 질문: 8-2
- 왜 효과적인가: 무엇을 건드리면 안 되는지 명확해서 AI가 스스로 범위를 지킴. 예: Citation 규칙이 원인이었을 때 AI가 고치지 않고 결정을 요청함. 보고 형식이 있어 결과를 비교하기 쉬움
- AI가 활용한 정보: 변경 금지 목록을 "지키지 못하는 상황" 판단 기준으로 사용

**② "원인부터 확인" + "조사만"**
- 실제 질문: 8-3, 8-4
- 왜 효과적인가: 섣부른 수정 없이 사실을 먼저 얻음. 2008 숫자, 로고 테두리, FAQ 미표시 모두 원인이 예상과 달랐음
- AI가 활용한 정보: 실제 DB·파일·픽셀 측정

**③ AI 결과의 이상한 숫자를 짚어 되묻기**
- 실제 질문: 8-5
- 왜 효과적인가: AI가 추정으로 넘긴 부분(답이 짧아서 빠름)이 실제로는 핵심 버그였음
- 교훈: AI 보고서의 "~일 수 있다"는 확인 요청 대상이다

**④ 안전 한계를 숫자로 정해 주기**
- 실제 질문: 8-6
- 왜 효과적인가: 기준값을 낮추는 쉬운 해결을 막아 "없는 내용을 지어내는" 위험을 차단. 없는 질문 5개라는 **반대 방향 검증**을 명시

**⑤ 사람이 판단할 비교 자료 요청**
- 실제 질문: "[현재 / 방식A / 방식B] 답변 전문을 나란히 비교하는 문서 … 내가 간호사로서 직접 읽고 품질을 판단할 거야"
- 왜 효과적인가: 방식 A가 빠르지만 답을 잃는다는 것을 사람이 보고 결정할 수 있었음

**⑥ "고치지 말고 먼저 알려줘"**
- 실제 질문: 8-12
- 왜 효과적인가: AI가 자기 문서의 날짜 오류까지 찾아냄. 결정권이 사용자에게 남음

**⑦ 큰 작업의 단계 분리와 중단 규칙**
- 실제 질문: 8-13
- 왜 효과적인가: 48개 항목을 3단계로 나누고 단계마다 빌드·테스트를 통과시킴. 55개 항목 대조 후 누락 0

**⑧ 다른 AI의 작업 이어받기**
- 실제 질문: 8-1
- 왜 효과적인가: 원래 명세 전체를 다시 줘서 AI가 명세와 실제 코드를 대조할 수 있었음

### 9-2. 효과가 낮았던 질문

**① "웹으로 보는 문서 중 html에" + 명세**
- 왜 부족했나: 문장이 끊겨 "어디에" 적용할지 불명확. docs_view는 정적 문서라 명세(실제 검색 결과 점수 표시)와 맞지 않음
- 필요했던 정보: 실제 SCHAT 관리자 화면인지, 설명 문서인지
- 더 좋은 질문 예시: "SCHAT 관리자 화면에서 답변마다 출처 옆에 검색 점수(문서명·페이지·vectorScore…)를 보여줘. 직원 화면에는 숨겨줘. 검색 로직은 바꾸지 마."
- 결과: AI가 선택지를 주고 물어서 해결됨(1회 왕복 추가)

**② "제대로 된게 맞는지 웹화면으로 보여줘"**
- 왜 부족했나: 운영 사이트인지 노트북인지, 어느 화면인지, 공유용인지 불명확. 병원 원문이 담긴 화면이라 공개 링크로 올리면 안 됨
- 결과: AI가 로컬 HTML(스크린샷 17장)로 만들고 외부 공유 금지를 안내함
- 더 좋은 질문 예시: "퀴즈 관리자·직원 화면을 노트북에서 실제로 찍어서 한 페이지로 보여줘. 병원 내용이 있으니 내 PC에만 저장해줘."

**③ "왜 안된다는거야?" + 스크린샷**
- 왜 부족했나: 어떤 계정에 무엇을 하려던 것인지 없음
- 결과: 스크린샷 덕분에 원인은 맞혔지만, AI가 "관리자 본인 계정이면 다른 행을 수정해야 한다"고 추가 확인을 해야 했음
- 더 좋은 질문 예시: "관리자인 내 계정에 사번 [REDACTED]을 넣으려고 수정 → 저장을 눌렀더니 이 오류가 나. 왜 안 되는 거야?"

**④ 너무 긴 대화에서 너무 긴 요청(1.0 마무리)**
- 왜 부족했나: 대화가 누적돼 요청 자체가 `Prompt is too long`으로 처리되지 않음
- 더 좋은 방법: 새 대화에서 시작하고, 첫 줄에 "CLAUDE.md와 현재 상태 문서를 먼저 읽어줘"라고 쓴다. 요청은 단계별로 나눈다

**⑤ 같은 요청을 두 번 보냄**
- 1.0 마무리 요청을 보냈다가 중단하고 바로 다시 보냄. 기록상 두 요청은 거의 같음. 수정한 부분이 있다면 무엇이 바뀌었는지 첫 줄에 쓰면 AI가 헷갈리지 않는다

## 10. 개발 과정에서 등장한 핵심 개념

| 개념 | 어디에서 등장 | 왜 필요했나 | 이 프로젝트에서의 역할 | 비개발자용 설명 |
|---|---|---|---|---|
| RAG | 전 과정 | AI가 병원 문서 근거로만 답하게 | 검색 → 근거 → Gemini 답변 → 출처 | AI에게 답하기 전에 관련 지침서 쪽을 먼저 찾아 붙여 주는 방식 |
| 임베딩(Embedding) | 검색, 속도 측정 | 뜻으로 찾기 | `gemini-embedding-2` | 글을 숫자 목록으로 바꿔 뜻이 비슷한 글끼리 가깝게 만드는 것 |
| 벡터 DB(ChromaDB) | 검색, 2008 조사 | 숫자로 바꾼 조각 저장·검색 | 본문 654 + 이미지 설명 1,331 | 뜻 검색용 창고 |
| 코사인 유사도 | 검색 점수 | 뜻의 가까움 측정 | 0.25 미만 제외, 0.7 이상은 단독 통과 | 두 글의 방향이 얼마나 같은지(0~1) |
| BM25 | 검색, 동의어, 띄어쓰기 | 정확한 단어(약어·시술명) 찾기 | 하이브리드의 25% | 질문 단어가 문서에 얼마나, 얼마나 드물게 나오는지로 매기는 점수 |
| 하이브리드 75:25 | 검색 점수 | 두 방식의 장점 결합 | `0.75÷vectorRank + 0.25÷bm25Rank` | 뜻 검색 등수와 단어 검색 등수를 3:1로 섞음 |
| 청킹(Chunking) | 멘토링 | 긴 문서를 검색 단위로 자르기 | 900자, 120자 겹침 | 지침서를 작은 조각으로 자르기 |
| Top-K / topN | 속도, 거르기 | 답변에 넣을 조각 수 | 보통 4개 | 몇 개까지 근거로 쓸지 |
| 거르기(post-filter) | 문제 20 | 약한 근거 제거 | 2/3 일치 또는 0.7 유사도 | 관련 없어 보이는 조각을 마지막에 빼는 단계 |
| Hit@10, MRR | 평가 | 검색 성능 숫자 | Hybrid 100%, 0.738 | 정답이 상위 10개에 있는 비율 / 정답이 얼마나 위에 있는지 |
