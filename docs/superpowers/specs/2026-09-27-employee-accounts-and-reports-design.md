# 직원 개인계정·일괄등록·문제 신고 설계

## 1. 현재 인증 구조(조사 결과)

| 항목 | 현재 |
|---|---|
| 사용자 표 | `users`(Prisma/SQLite): `id`, `username`(고유, 영문 소문자 시작), `password`, `role`(`default`/`manager`/`admin`), `suspended`, `createdAt`, `lastUpdatedAt` 등 |
| 로그인 | `POST /api/request-token`: 아이디로 조회 → bcrypt 비교 → 정지 여부 확인 → JWT(`{id, username}`, 기본 30일) 발급. 첫 로그인 때 복구 코드를 보여 줌 |
| 비밀번호 | `bcryptjs`로 해시만 저장. 응답에서는 `User.filterFields`가 해시를 제거함 |
| 권한 | `role` 문자열. 서버는 `strictMultiUserRoleValid`/`flexUserRoleValid`로 API마다 검사 |
| 정지 | 요청마다 `validatedRequest`가 `suspended`를 확인하므로 사용중지는 즉시 적용됨 |
| 비밀번호 변경 | 복구 코드 기반 재설정(`/system/recover-account`, `/system/reset-password`)과 관리자 수정(`/admin/user/:id`)은 있음. 본인 변경 화면과 "최초 로그인 강제 변경"은 없음 |
| DB 변경 | 컨테이너 시작 때 `prisma migrate deploy`가 자동 실행됨 |
| Excel | 서버에 `exceljs` 4.4.0이 이미 설치되어 있어 새 의존성 없이 xlsx 읽기·쓰기 가능 |
| 문제 신고·알림·FAQ·통계 | **현재 코드와 DB에 없음.** 이번에 새로 만들어야 함 |

## 2. 설계 원칙

- 새 인증 시스템을 따로 만들지 않고 `users`, bcrypt, JWT, `validatedRequest`를 그대로 씁니다.
- 기존 계정은 지우지 않습니다. 새 칸은 모두 비어 있어도 되는(nullable) 칸으로 추가합니다. 따라서 기존 관리자·직원 계정은 기존 아이디/비밀번호로 계속 로그인할 수 있습니다.
- 내부 연결(권한·신고·알림)은 모두 `users.id` 기준입니다. 이름으로 사람을 찾지 않습니다.

## 3. DB 변경(추가 전용 migration 1개)

- `users`에 칸 추가(모두 nullable 또는 기본값 있음):
  - `employee_number`(고유)
  - `display_name`
  - `department_id`
  - `must_change_password`(기본 false)
  - `password_changed_at`
  - `last_login_at`
  - `disabled_at`
  - `username`은 그대로 두고, 사번 계정은 내부적으로 `emp-<사번>`을 넣습니다.
- 새 표 네 개:
  - `departments`: `id`, `name`(고유), `active`, `sort_order`, 시각. 직원이 있는 부서는 삭제하지 않고 사용중지만 합니다.
  - `issue_reports`: 신고자 `reporter_user_id`, 신고 당시 이름·사번·부서·권한 snapshot, 종류, 제목, 내용, 관련 기능, 상태(미처리/처리중/완료), 처리 결과, 처리 관리자, 시각
  - `user_notifications`: `user_id`, 신고 id, 종류, 문구, `read_at`, 시각
  - `faq_items`: 제목, 종류, 키워드, 문제 상황, 해결 방법, 활성 여부, 원본 신고 id
- 권한: 화면의 `일반사용자` = `default`, `관리자` = `admin`입니다(`manager`는 앞선 결정대로 화면에서 쓰지 않음).

## 4. 로그인

- 기본 화면: 부서(선택) / 사번 / 이름 / 비밀번호
- 서버 확인 순서: 사번 조회 → 사용중 여부 → 부서 일치 → 이름 일치(앞뒤·연속 공백 정리) → bcrypt
- 실패하면 어떤 이유든 "로그인 정보를 다시 확인해주세요."만 보입니다. 기록에는 입력값을 남기지 않고 실패 종류와 IP만 남깁니다.
- 기존 관리자(사번 없음)는 로그인 화면 아래 `관리자 로그인` 링크로 기존 아이디/비밀번호 방식을 그대로 씁니다. 원하시면 나중에 관리자에게도 사번을 등록할 수 있습니다.
- `must_change_password`가 켜져 있으면 로그인 직후 비밀번호 변경 화면만 보이고, 서버도 다른 API를 막습니다.
- 사번 계정에는 복구 코드 화면을 띄우지 않습니다. 비밀번호를 잊으면 관리자가 초기화합니다.

## 5. 사용자 관리(관리자)

- 목록: 이름, 사번, 부서, 권한, 상태, 최근 로그인
  - 검색: 이름·사번
  - 필터: 부서·권한·상태
- `직원 추가`(한 명): 이름·사번·부서·권한·사용 여부를 받고 임시비밀번호를 자동 생성합니다. 생성 직후 한 번만 보여 줍니다.
- 수정: 부서 이동, 이름 변경, 권한 변경, 사용중지/재사용. 계정 id·사번·비밀번호·과거 신고는 그대로 유지합니다.
- 비밀번호 초기화: 새 임시비밀번호를 만들고 `must_change_password`를 켭니다. 기존 비밀번호는 누구도 볼 수 없습니다.
- 부서 관리: 추가, 이름 변경, 사용중지. 직원이 있는 부서는 삭제할 수 없습니다.
- 임시비밀번호: 12자, 암호학적 난수로 만들고 헷갈리는 글자(0/O, 1/l)는 뺍니다. 직원마다 다릅니다.

## 6. 직원 일괄등록(신규 전용)

1. `일괄등록 양식 다운로드`(xlsx)
   - 1번 시트 제목 줄: `부서 | 사번 | 이름 | 권한`
   - 2번 시트: 권한 입력값과 현재 사용중인 부서 목록 안내
2. 파일 올리기(xlsx 또는 csv, 5MB·1,000행 이하)
   - 서버가 메모리에서만 읽고 파일을 저장하지 않습니다. 직원 정보를 로그에 쓰지 않습니다.
3. 등록 전 확인: 총 N명 / 정상 / 오류(행 번호·사번·사유)
   - 검사 항목: 필수 칸, 빈 행, 부서 누락·없는 부서, 사번·이름 누락, 잘못된 권한, 파일 안 사번 중복, 이미 등록된 사번(`이미 등록됨`, 덮어쓰지 않음), 같은 사번인데 이름·부서가 다른 행, 지원하지 않는 형식
4. `정상 N명 등록` 또는 `취소`
   - 서버가 확인 결과를 10분짜리 일회용 토큰으로 기억합니다. 등록할 때 다시 검사하고 한 번의 DB 트랜잭션으로 만듭니다.
   - 같은 토큰은 한 번만 쓸 수 있고 사번 고유 제약이 있어, 버튼을 여러 번 눌러도 중복 계정이 생기지 않습니다.
5. 결과: `N명의 계정이 생성되었습니다.`와 `부서 | 사번 | 이름 | 임시비밀번호` 표. `등록 결과 다운로드`(xlsx)는 브라우저에서 만듭니다. 서버에 임시비밀번호를 다시 조회하는 기능은 두지 않습니다.

- 부서 이동·사용중지 일괄 처리는 신규등록과 분리된 `직원 정보 일괄수정`으로 구조만 준비하고 이번에는 만들지 않습니다(개별 처리는 가능).

## 7. 문제 신고·알림·FAQ·통계(신규)

- 직원 화면
  - 사용자 메뉴에 `문제 신고`, `내 신고`, `비밀번호 변경`, `로그아웃`. 오른쪽 위에 알림 종 아이콘(읽지 않은 수)
  - 신고 입력: 종류·제목·내용(필수), 관련 기능(선택). 개인정보 입력 금지 안내를 표시합니다. 신고자는 로그인 계정에서 자동 연결됩니다.
- FAQ 추천: 제목·내용을 입력하면 활성 FAQ를 키워드로 찾아 보여 줍니다. 외부 AI는 호출하지 않습니다. `도움이 됐어요` / `그래도 문제 신고`를 제공하며, 신고를 막지 않습니다.
- 관리자 화면(`SCHAT 관리자 설정 > 문제 신고`)
  - 목록: 번호·제목·종류·신고자·사번·부서·등록일·상태
  - 검색: 제목·내용·이름·사번
  - 필터: 부서·종류·상태·기간
  - 상태를 `처리중`으로 바꾸거나 `완료`로 바꾸면 신고자에게만 알림이 갑니다.
  - 완료된 신고는 `FAQ로 등록`할 수 있습니다.
- 통계: 전체, 상태별, 최근 7일·30일, 평균 처리시간, 종류별, 부서별(신고 당시 부서 기준). 직원 개인 순위는 만들지 않습니다.
- 권한은 서버에서 검사합니다. 직원은 자기 `user_id`의 신고·알림만 조회·읽음 처리할 수 있고, 관리자 API는 `admin`만 호출할 수 있습니다.

## 10. 변경(2026-09-27): 임시비밀번호 폐지, 처음 로그인에서 직접 설정

- 사용자 요청: 수백 명에게 임시비밀번호를 전달하는 운영이 어렵다.
- 새 계정과 관리자가 초기화한 계정은 `must_change_password=true`이고, 비밀번호 칸에는 아무도 모르는 무작위 값의 해시를 넣습니다. 이 상태에서는 어떤 비밀번호로도 로그인되지 않습니다.
- 로그인에서 부서·사번·이름이 이 상태의 계정과 일치하면 `firstLoginRequired`를 돌려주고, 화면은 `처음 로그인`(새 비밀번호·확인)으로 이동합니다.
- `POST /api/schat/first-login`은 이 상태일 때만 성공합니다. 조건부 update로 동시 요청도 한 번만 성공하며, 설정 뒤에는 다시 들어갈 수 없습니다.
- 이 상태의 계정은 기존 세션도 모든 API에서 401로 막힙니다. 관리자가 초기화하면 기존 로그인 창이 즉시 끊깁니다.
- 알려진 위험: 비밀번호를 정하기 전에는 부서·사번·이름을 아는 다른 사람이 먼저 비밀번호를 정할 수 있습니다. 본인은 로그인할 수 없게 되어 알아챌 수 있고, 관리자 초기화로 되돌릴 수 있습니다. 처음 설정은 `first_login_password_set`, 실패는 `failed_first_login`으로 기록합니다.
